# 設計：v2 幾何エンジン（RSS駆動・世界地図）2026-07-30

## 0. 位置づけと手戻り方針

本書は**実装前の設計確定**を目的とする。方針転換の背景は `docs/課題整理_ハーネス設計と自律の壁_2026-07-30.md` を参照。
原則：**一番やり直しが痛い決定（データモデル・クラスタ同一性）を先に紙で固定し、本番コードはその後**に書く。これが最大の手戻り防止である。プロトタイプ（`scratchpad/world_map_*.py` と公開した世界地図Artifact）で幾何アプローチの有効性は実証済み。

---

## 1. 実データから確定した制約（設計の根拠）

- `rss_candidates`（ingest時）＝ **title ＋ snippet（中央値87字）**。本文は無い。
- `deep_research`（Web取得後・28/41件）＝ **results 最大14KB / synthesis 最大2KB**。
- 帰結：**リッチな概念情報は"取得後"にしか存在しない。** 全記事に概念抽出を先付けする設計は無駄。

---

## 2. 点モデル（「記事＝点」対「概念＝点」の決着）

二択ではなく**二層**とする。どちらの作業も捨てない。

- **Tier0（安価・全点）**：title+snippet の埋め込み（EmbeddingGemma 768d）。多様体・密度・GAP検出はこれで十分（プロトで実証：宇宙/量子/EV/食品安全などのテーマとGAPを正しく再現）。
- **Tier1（高価・オンデマンド）**：`deep_research.synthesis` から概念を抽出。**ページ化・深掘り対象に選ばれたクラスタのメンバーだけ**に適用。

ingest は Tier0、ページ化は Tier1。概念抽出をコスト高な所に限定でき、手戻りも無い。

---

## 3. クラスタ同一性（本設計の心臓・最大の手戻り源）

**問題**：毎run全再クラスタリングするとクラスタIDが揺れ、「ページ↔クラスタ」対応が壊れる。プロトの単連結→平均連結の改良は"1枚の地図"としては妥当だが、**ストリームで増える運用**には持続的な同一性が要る。

**方針：永続クラスタ**。DBに `clusters(cluster_id, centroid_blob, size, updated_at, page_path NULL)` を持つ。

- **新点の割当**：最近傍クラスタ重心と `cos ≥ θ_attach` なら所属、未満なら新クラスタを seed。
- **定期再整理**：近すぎるクラスタを併合（`θ_merge`）、分散しすぎたクラスタを分割。
- **centroid はインクリメンタル更新**（全再計算しない）。

これにより**ページはクラスタIDに固定**され、記事が増えても対応が壊れない。プロトの平均連結は「初期クラスタの一括生成（bootstrap）」に使い、以降は attach/seed で増分維持する。

---

## 4. ページのライフサイクル（記事1:1変換と重複の廃止）

- **生成**：クラスタが密度しきい値（実点 ≥ K）を超えたら、そのメンバーの `deep_research` を材料にLLMが**1ページ合成**。
- **改善**：既存クラスタに新点が着地 → 対応ページを improve。
- **減衰**：新点が来ないまま aged → stale → archive。無限増殖を抑え「生きた地図」を保つ（既存 `stale_days` 機構を流用）。

効果：**「ページ＝密度の高いクラスタ」**なので、
- 現行の病理（記事を1対1でページ化＝17ページが浅い近重複）が**設計から消える**。
- クラスタ同一性により**重複ページが原理的に出ない**（現行の `find_similar_page` 事後dedupが不要化）。

---

## 5. 層A（機構安定）との接続

- **幾何が"有効な選択肢メニュー"を生成**：`{ create_page(cluster c) | improve_page(cluster c) | watch(frontier) }`。cluster参照は**ID＝閉じている**ので不正target（`path escapes vault` 等）が原理消滅。
- **LLMはメニュー内で判断＋本文生成**。`resolver` は任意出力を妥当opへ写像し **raise しない**（`plan_rejected` を結果から消す）。
- **Reviewer は別モデル**へ分離、原則 warning 降格（`課題整理` doc §5 準拠）。

これで「自律を削らず（＝何を書くべきかは幾何＋LLMが決める）機構だけ安定させる」が成立する。

---

## 6. run ループ v2（1回の実行）

```text
1. RSS取り込み → 新点を Tier0 埋め込み → 永続クラスタへ attach/seed
2. 定期再整理（併合 / 分割 / 減衰）
3. 幾何がメニュー生成:
     密度超え×未ページ化クラスタ → create候補
     新点着地×既存ページ持ちクラスタ → improve候補
     孤立点 → watch（フロンティア）
4. 対象クラスタのメンバーを deep_research（未取得のみ）→ Tier1概念
5. LLMが本文合成/改善 → resolver → Reviewer(別モデル) → 保存
     → page_path をクラスタに紐付け
6. runs / reflections へ記録
```

---

## 7. 実装順序（手戻り最小・各段は可逆）

移行用フラグは**後方互換のためではなく、安全な段階移行のため**の一時措置。S4検証後に旧経路は削除する（恒久的な後方互換は残さない）。

- **S1**：`clusters` テーブル＋attach/seed を追加。**書き込み系に触れず**、毎run地図を更新するだけ（＝完全に可逆・観測のみ）。
- **S2**：定期再整理（併合/分割/減衰）。まだページ生成に触れない。
- **S3**：メニュー生成を Planner に接続（既存Plannerと**切替フラグ**）。
- **S4**：ページ生成を「クラスタ起点」に切替（旧1:1経路をフラグでオフ）。
- **S5**：Reviewer 別モデル化・resolver 全域関数化。

各段でロールバック可能。S1〜S2は現行運用を一切壊さないので、**まずここから着手するのが最も安全**。
