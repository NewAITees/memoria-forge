# 課題整理：ハーネス設計と自律の壁（2026-07-30）

## 0. この文書の位置づけ

本文書は、既存の討議資料 `docs/AI議論用_自律Wiki構築AI_現状と課題.md`（2026-07-22）を**補完・更新**するものである。
7/22版が「機能一覧と品質課題の列挙」であったのに対し、本文書は実運用データ（約1週間・142run）と設計議論を踏まえ、**「なぜ安定しないのか」を層の問題として再定義**することを目的とする。

結論を先に述べる。本プロジェクトの不安定さは、**モデルの非力さが主犯ではなく、"自律のさせ方"（ハーネス）の設計が事後対症療法に留まっていること**、および**AIが目標表象を持たないこと**の2点に由来する。

---

## 1. 目標の再確認

本プロジェクトの芯は「LLMに知識を保存させること」ではない。
**AIが人の介在なしに自律的に動き、自分で何かを立ち上げて完成させること**（いわゆる computer-use / 自律エージェント系のゴール、OPENCLAW的な"AIが自律的に動く"こと）にある。

したがって、**自律性を削って安定させる解決は、目標そのものの否定になる**。
「直線的な無状態パイプラインに落とせば安定する」は事実だが、それは「今のプログラムでよい／作る意味がない」に帰着するため、採用しない。

守るべき制約：**自律を1ミリも削らずに安定させる**こと。

## 3. 根本原因分析

### 3.1 失敗は「生成」ではなく「メタ判断」に集中している

最重要の観察。失敗系の内訳を見ると：

- **生成（Writer）は118回成功**している。
- 落ちているのは **plan_rejected(7) と review_rejected(14) = 計21件**、すなわち
  - `plan` … 次に何をするかを**自分で決める**タスク
  - `review` … 自分の成果を**自分で審査してゲートする**タスク

つまり、**このモデルは「生成」では十分安定しており、壊れているのは"メタ判断"の層だけ**である。

この観察は「モデルが小型だから不安定」という仮説を否定する。反例として、別プロジェクトでは 3n E4B 級（約4B）が RSS→ネットリサーチ→レポート生成を**安定して**こなしている。差はモデルの賢さではなく、そのタスクに **Planner も自己レビューのゲートも存在しない**ことにある。

### 3.2 事後catch式の実装は原理的に収束しない

`tasks/lessons.md` の約26項目は、よく見るとほぼ全て同じ構造をしている：
**「モデルが想定外の形を返した → 後から検出して個別に直す」**。

- 二重フロントマター、コードフェンス包み、`\n`リテラル、キー揺れ（synthesis/summary/content）、拡張子なしターゲット、Vault逸脱パス、毒キュー、push競合、staleロック…

モデル出力は毎回揺れるため、**揺れを事後に潰し続ける方針は永遠に別の揺れを生む**。1週間の不安定さの体感的な正体はこれである。

### 3.3 単一モデルの自己完結ループ

Planner・Writer・Reviewer が**すべて同一のローカルモデル（qwen3:8b）**。
自分で書いて自分で審査するため、レビューが弱く、`review_rejected` の判定が毎回ぶれる。これはサイズの問題ではなく、**審査が生成と同じ分布から出ている**構造の問題。

### 3.4 状態蓄積系の事故

共有Vaultを書き換え続ける設計ゆえに、直線パイプラインには存在しない事故が起きる：
重複ページの累積、毒タスクのキュー残留、staleロックによる無限スキップ。

### 3.5 【核心】目標表象・収束の欠如（層B）

最も深い原因。現在のエージェントは **「このWikiを最終的にどこへ持っていくか」という目標表象を持っていない**。

そのため「妥当だが無意味な作業」を無限に繰り返せる（例：最小ページを延々と再改善する → cooldownで場当たり対処した既知の挙動）。
**142run 回して17ページで空回りした真因は、機構の破損だけでなく、"何を完成させようとしているか"をAIが保持していないこと**にある。

---

## 4. 問題の再定義：「自律 vs 安定」は偽の二択

「自律を上げると壊れる」のではない。壊れているのは**自律の実装が脆いこと**である。
安定を2種類に分けると議論が滑らない：

- **機構としての安定（層A）**：クラッシュしない・ロックで詰まらない・不正/重複ページを吐かない・毎回1周回る。
  → ユーザーが報告した症状はこちら。**自律を保ったまま到達可能。**
- **判断としての安定（層B）**：月単位でWiki全体が良質・整合的に育つ。
  → 小型・無監視では今なお難しいフロンティア。

**自律が宿る場所（何を作るかの意思決定）と、安定が宿る場所（それを妥当な操作に変換する機構）は分離できる。**
memoria-forge が壊れたのは、この2つを融合し、AIに「意図」と「実行可能な生の文字列」を同時に吐かせていたため、表現の揺れがそのままクラッシュになっていたからである。

---

## 5. ハーネス再設計の方針（層A：機構安定）

### 5.1 不変条件（最重要）

> **ハーネスはAIの決定を"形式"で却下してはならない。どんなAI出力も、必ず"最も近い妥当な操作"へ強制変換して前進させる。**

現状の `validate_action` / `repair_plan` は「形が変なら例外／plan_rejected」であり、却下＝停止＝不安定を生む。
これを **resolver（全域関数）：任意のAI出力 → 必ず妥当なアクション** に置き換える。
既存の `safe_new_page_target` / `resolve_target_for_duplicates` / `choose_candidate` フォールバックは、この全域関数へ**部分的に到達していたパッチ群**であり、「resolverは絶対にraiseしない」を一級の不変条件へ昇格させる。

### 5.2 4層構成

```text
1. Affordances（状態→参照メニュー）
   既存ページにIDを付与、staleページ、キュー、検出した空白トピックを列挙
        ↓
2. Decision（スキーマ拘束デコード）
   AIが {action: enum, target: 既存ID | new_title: 自由文字列, reason} を返す
   action は enum に、target は「有効ID」か「自由タイトル」に、デコーダレベルで強制
        ↓
3. Resolver（全域関数・却下しない）
   既存ID→実パス（必ず実在）／ new_title→正規化+dedupリダイレクト
   使えない出力→決定的フォールバック。例外なし・却下なし
        ↓
4. Executor
   解決済み操作を実行
```

### 5.3 自律をどこに残すか（スライダー）

- メニューをハーネスが固定ルールで全列挙し AI が選ぶだけ → 100%妥当だが**"何を作るか"を決めているのは実質ハーネス**＝自律が偽物化。
- AI が **new_title で方向そのものを発明**し、ハーネスは**却下せず正規化するだけ** → 自律は本物。ただし正規化（層3）が強靭であることが前提。

**memoria-forge は明確に後者寄りに置く**：「既存ページへの参照はID（閉じる）／新規の方向はAIが自由発明（開く）／ハーネスは発明を正規化するが拒否しない」。

### 5.4 個別の具体策

- **スキーマ拘束デコード**：Ollama/llama.cpp の GBNF文法・structured output で plan/review JSON をデコーダレベルで強制 → キー揺れ・JSON途中切れ・独自スキーマ系が原理消滅。
- **エージェント相互レビュー**：自己レビューをやめ、2つ目のモデルインスタンス（別モデル可）に審査させる。人間は入らない＝自律を保ったままレビュー品質を上げる。
- **ブロッキングの最小化**：Reviewer は原則 warning ログに降格。ハード安全（injection・プレースホルダ・空）だけを**ハーネス側が決定的に**判定してブロック。

## 6. 外部事例からの裏付け：Fara1.5 / Holo3.1

※以下は共有された資料の記載内容を前提とする（各版の実在・スペックは本文書では未検証）。

2つの computer-use エージェント（Fara1.5 / Microsoft、Holo3.1 / H Company）は、**「重み（HF）とハーネス（GitHub）を必ずセットで公開**」している。Microsoft は「fara CLI か MagenticLite **以外では使うな**」と明記。理由は、アクション出力が `<tool_call>...</tool_call>`（XMLで包んだJSON）という**固定形式**であり、それに合わせた**専用パーサ（ハーネス）でないと解釈できない**ためである。

これは本プロジェクトの結論の実物の裏付けである：

| 本文書の層 | Fara / Holo での実装 |
|---|---|
| Affordances（観測の固定） | Vision-only・学習解像度1440×900に合わせろ＝入力分布をピン留め |
| Decision（拘束された出力） | `<tool_call>` 固定形式 / function calling・JSON出力＝ワイヤ形式＋専用パーサ |
| Resolver / Executor（安全実行） | MagenticLite の Quicksand（QEMUサンドボックス）＝隔離実行 |
| 目標表象・分解（＝層B） | MagenticBrain（オーケストレータ）＋承認フロー |

**学び：**
- モデルは単体では製品にならない。**モデル＋ハーネスが製品**である。
- 出力の揺れは「事後catch」ではなく**ワイヤ形式の固定＋専用パーサ**で殺している（本文書§5.4と一致）。
- MagenticLite は「承認フロー」を一級機能としてハーネスに持つ（自己レビュー問題への現実解）。
- Holo は「Claude Code / Cursor / Codex からサブエージェントとして呼ばれる」＝自律ユニットを綺麗な契約で公開。

**ただし重要な限界：** これらは GUI操作エージェントであり、
- アクション空間が**画面という物理で有界**（クリック/タイプ/スクロール）、
- **ゴールは毎回、人間のタスクプロンプト由来**（自己起点の目標生成をしない）。

すなわち **これらは層A（モデル出力→妥当操作）を美しく解くが、層B（自己起点の収束・目標表象）は人間/オーケストレータに外出しして回避している**。
memoria-forge の「17ページ空回り」の真因である層Bは、これらを持ってきても埋まらない。
→ 逆に言えば、**「層Aはこう解ける、だからエネルギーは層Bに全部注げ」**というメッセージとして読める。

## 7. 未解決の核心（層B）：論点

1. **目標表象をどう表現するか。** 「このWikiをどこへ持っていくか」をAIが保持し、毎runそれに照らして選ぶ形をどう作るか。
2. **gap（何が足りないか）を誰が決めるか。** 固定ルール検出では自律が頭打ち。AIに提案させるなら層3の正規化が任意のnew_titleを安全に飲めることが前提。→「AI提案・ハーネス正規化」を採る。
3. **収束（完成の定義）を誰が持つか。** 「トピックXは十分育った」という判断がないと、妥当な作業を無限に空回りする。

## 8. 選択肢と推奨順序

**目標の芯（AIが自分で作り上げる）を殺さない前提での選択肢：**

1. **エンジンを上げて自律を保つ**：Writer/Reviewer を分離・強化（フロンティアAPI or 別モデル）。目標に最も忠実。
2. **自律の"幅"を狭める**：対象を絞る（例：RSS 1本→1ページ）。作り上げる体験は残るが自律の射程は縮む。
3. **実験として畳む**：「小型・無監視の完全自律はここまで壊れる」という知見（lessons.md）を成果として確定し区切る。

**推奨する実行順序：**

1. **層A（機構安定）をまず入れて止血** … `validate_action`/`repair_plan` の却下を、全域関数 resolver に置換。plan_rejected / review_rejected を「結果」から消す。
2. その動く土台の上で **層B（目標表象つきハーネス）を設計** … 本プロジェクトの本丸。ここが「自律してるフリ」と「実際に作り上げる」を分ける最後の一線。

現状の資産（Planner/Writer/Reviewer 分離、reflection、テスト、health report、経路A=RSS深掘り）はそのまま活きる。
