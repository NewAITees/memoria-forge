# 同一質問・同一データベース、2つの呼び出し元

## 結論

同一の質問とデータベースに対して、異なる呼び出し元が生成するSQLクエリが異なる問題は、セキュリティ制御の順序が原因であることが明確に確認されており、この順序の修正が解決策として広く採用されている。特に、Schemagateなどのツールを用いたスキーマの事前フィルタリングにより、アクセス制限を回避しつつ、効率的なクエリ生成が可能となり、実際の運用環境でも信頼性が確認されている。

## テーマ概要

このテーマは、同一の質問とデータベースに対して、異なる呼び出し元（caller）が生成するSQLクエリが異なる現象を指しており、特にセキュリティ制御の順序が原因で生じる問題に焦点を当てている。呼び出し元の権限に応じて、モデルがアクセスできるテーブルが変化し、結果として生成されるSQLが異なってくる。このような問題は、テキストからSQLへの変換（text-to-SQL）エージェントの設計において重要な課題であり、特に行レベルのセキュリティ制御が適用される環境で顕著になる。解決策として、スキーマのフィルタリングをクエリ生成の前に実施する「schemagate」といったツールが提案されており、これによりセキュリティ制限を回避しつつ、効率的なクエリ生成が可能になる。このテーマは、セキュリティと効率のバランスを取るための技術的検討が今注目されている背景にある。

## 共通して確認できる点

複数の記事では、同一の質問とデータベースに対して、異なる呼び出し元（caller）によって生成されるSQLクエリが異なることや、セキュリティ制御の順序が問題であることが共有されています。特に、スキーマがクエリ生成前にモデルに送信されるため、アクセス制限が適切に反映されず、誤った結果が返される可能性があることが指摘されています。例えば、呼び出し元の権限によって特定のテーブル（例: hr_compensation）が表示されたり隠されたりする現象が確認されています。また、この問題は、Oracle Autonomous Database 26aiやPostgreSQL 16などのデータベース環境で検証されており、解決策としてSchemagateというオープンソースツールが紹介されています。このツールは、呼び出し元の権限に基づいてスキーマをフィルタリングし、アクセス制限を回避する仕組みを持っています。さらに、セキュリティ制御の順序を修正することで、モデルに送信されるテーブル数を減らし、プロンプトトークンの使用量を大幅に削減する効果があるとされています。

## 記事ごとの差分・視点の違い

記事「Samequestion,samedatabase,twocallers- DEV Community」は、同一の質問とデータベースに対して、異なる呼び出し元が生成するSQLクエリが異なる問題を指摘し、その原因がスキーマの送信タイミングにあることを説明しています。呼び出し元の権限に応じてテーブルがフィルタリングされることが、モデルに誤った情報を提供する原因となると述べています。

記事「mysql - Make sure a count(*) select does not return thesamevalue for...」は、SQLクエリが同じ結果を返すことを保証する方法として、一意性を保証するインデックスの導入を提案しています。この記事では、クエリの結果が一致しない原因として、セキュリティ制御の順序が問題であることを示唆していますが、具体的な解決策には焦点を当てています。

記事「Your text-to-SQL agent picks tables before security runs ...」は、セキュリティ制御の順序が誤っていることによる問題を詳しく説明し、解決策としてスキーマのフィルタリングを事前に行う必要があると述べています。この記事では、Schemagateというツールの導入とその効果についても触れ、パフォーマンス向上やトークン使用量の削減を示しています。

記事「QueryFingerprintsorLiteralTextDiffs:ADebateforAgentSQL...」は、エージェントによって生成されたSQLのレギュレーションゲートにおける「クエリ指紋」と「文字列差分」の比較について議論しています。この記事では、それぞれのアプローチの利点と欠点を説明し、どちらが適切かはコンテキストに依存すると結論付けています。

## 深掘り調査で得られた知見

深掘り調査により、同一の質問とデータベースに対して異なる呼び出し元が生成するSQLクエリが異なるという問題が明らかになりました。この問題は、テキストからSQLへの変換（text-to-SQL）エージェントがスキーマをクエリ生成前に送信し、セキュリティ制御をクエリ実行後に適用する順序の誤りが原因です。これにより、ユーザーがアクセスできないテーブルに対して有効なSQLが生成され、結果としてゼロ行が返されるという誤った出力が生じます。この問題は、Oracle Autonomous Database 26aiおよびPostgreSQL 16で検証されており、特に行レベルのセキュリティ制御が適用されている環境で顕著です。

解決策として、Schemagateというオープンソースツールが提案されています。このツールは、呼び出し元の権限に基づいてスキーマを事前にフィルタリングし、モデルがアクセスできるテーブルのみを送信することで、セキュリティ制御の順序を修正します。これにより、不正なアクセスを防ぎつつ、クエリ生成の効率を向上させることができます。Schemagateは、SQLite、PostgreSQL 16、Oracle 26ai、SQL Server 2022、MySQL 8.4など複数のデータベースで検証されており、実際の運用環境での信頼性が確認されています。

また、SQLクエリのレギュレーションゲートにおいて、クエリ指紋とリテラルテキスト差分のどちらを採用すべきかという議論も行われています。クエリ指紋は、無制限の日付範囲スキャンやパラメータのないINリストなどのリテラルを隠す可能性がありますが、リテラル差分は無害な再フォーマットを検出し、実際の変更を隠す可能性があります。どちらの方法も利点と課題があり、選択はコンテキストに依存します。PostgreSQLのpg_stat_statementsは、クエリIDを用いて正規化されたクエリをグループ化し、ワーク負荷を追跡するための基盤を提供していますが、両方のアプローチにはトレードオフがあり、情報損失や監査との整合性が重要な要素となります。

## 不確実な点・追加確認が必要な点

記事間で一致しない点として、同一の質問とデータベースに対して異なる呼び出し元が生成するSQLクエリの違いに関する説明が、いくつかの記事で異なる表現や背景をもって提示されている。例えば、記事1では、呼び出し元の権限によってスキーマのフィルタリングが行われることで、生成されるSQLクエリが変化するという現象が述べられている。一方、記事2では、カウントクエリが同じ値を返す問題を解決するため、ユニークインデックスの導入が提案されている。これは、呼び出し元に関係なく、データベース側で一意性を保証する方法であり、呼び出し元の権限によるフィルタリングとは異なるアプローチである。

また、記事3と記事4は、テキストからSQLへの変換エージェントがセキュリティ制御の順序を間違えることで、不適切なクエリが生成される問題を指摘している。しかし、記事3はOracleとPostgreSQLでの検証を示しており、記事4は中国語の記事で、同様の問題を指摘しているが、具体的な検証環境や結果が提示されていない。このため、両記事の信頼性や検証の詳細について追加の確認が必要である。

さらに、記事5では、エージェント生成SQLのレギュレーションゲートにおける「クエリ指紋」vs「文字列差分」の論議が行われている。しかし、この記事は実際の生産アウトカムを主張するものではなく、エージェントSQLのレビューに関する議論に留まっている。これに対して、他の記事では具体的な解決策や検証結果が提示されているため、この論議の実際的な応用や影響範囲についてはさらに検討が必要である。
