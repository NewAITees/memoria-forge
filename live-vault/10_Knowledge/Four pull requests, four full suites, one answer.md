# Four pull requests, four full suites, one answer — プルリクエスト処理のコストと効率

## 結論

Pull Request（PR）の処理におけるテストスイートの実行コストは、プロジェクト規模の拡大とともに顕著に増加し、マージキューの導入によって処理効率が向上したことが明確に示されている。一方で、PRの測定や茶の量の測定は異なる文脈であり、直接的な関連性は確認されていない。また、Scrumプロセスの限界と、予測不可能な作業への対応策についての知見は、チームの柔軟な計画立案の重要性を強調している。

## テーマ概要

このテーマは、ソフトウェア開発におけるPull Request（PR）の処理とテストスイートの実行に関する課題を扱っている。特に、複数のPRが並行して処理される中で、それぞれにフルスイートを実行する必要性が生じ、それがチームの効率やコストに与える影響が焦点となる。この記事では、プロジェクトの成長に伴うテストスイートの負荷増加や、マージキューの導入による実行効率の改善など、実際の開発現場での課題と対応策が詳述されている。また、PRの処理方法やテストの実行戦略が、チームの生産性や信頼性に直結しているため、現在注目されている。

## 共通して確認できる点

複数の記事で共通して確認できた事実として、Pull Request（PR）の処理におけるテストスイートの実行コストが大きな課題となっていることが挙げられる。特に、プロジェクト規模の拡大に伴い、各Pull Requestに対してフルスイートを実行する必要性が生じ、その結果、リソース消費が増加している。また、テストスイートの実行時間は13〜19分とされ、そのうち93%がテストステップに占められ、一部のテストはリアルなプロセスを立ち上げたり、リアルなデータベースを移行したりするなど、高コストな処理を含んでいる。このような状況下で、マージキューの導入により、処理効率が向上し、マージごとの処理時間が1分半程度に短縮されている。一方で、PRの数や実行戦略はプロジェクトの規模やテストの種類によって異なり、一概に同じ対応が可能ではない。また、PRの測定はソフトウェア開発の文脈に限定され、他の分野（例：茶の測定）とは直接的な関連性が確認されていない。

## 記事ごとの差分・視点の違い

記事「Four pull requests, four full suites, one answer」では、Pull Request（PR）ごとにフルスイートテストを実行するプロセスのコストとその改善策について議論されている。プロジェクトの成長に伴い、テストスイートの実行時間が増加し、マージキューの導入によって効率化が図られた。一方、「I have 4 pull requests approved, but got achievement only for one, it's ...」では、GitHubのアチーブメント制度におけるPRの測定基準について触れられており、PRの承認数や共著コミット数が評価の条件となる。また、「Measuring the Tea Break」では、ソフトウェア開発におけるPRの測定と、茶の量の測定が異なる文脈であることを強調し、両者に直接的な関連性はないとされている。「How Much Loose Leaf Tea Should I Use per Cup?」では、茶の量の測定方法と、その標準化について詳しく説明されており、具体的な測定基準が提示されている。最後に、「Scrum Myths We Retired After Thursday Spillover」では、Scrumプロセスの限界と、予測不可能な作業への対応策について述べられており、スプリント計画における柔軟性の重要性が強調されている。

## 深掘り調査で得られた知見

深掘り調査により、Pull Request（PR）の処理におけるテストスイートの実行戦略についての詳細な知見が得られた。プロジェクトが成長するにつれ、各Pull Requestに対してフルスイートを実行する必要性が生じ、そのコストが課題となった。具体的には、フルスイートの実行時間は13〜19分で、テストステップが全体の93%を占め、一部のテストはリアルなプロセスを立ち上げ、リアルなデータベースを移行しており、これらが全体の41%を占める。一方で、他の10,750のテストは47秒以内で完了する。このような状況では、テスト数の削減が解決策にならないことが確認された。マージキューの導入により、実行効率が向上し、マージごとの処理時間が1分半程度に短縮されている。また、Pull Requestが他のPull Requestの後ろに待機する場合、その影響が発生する可能性がある。プロジェクトの規模やテストの種類によって、実行戦略は異なる可能性がある。この記事は、Pull Requestの実行戦略についての詳細な分析を提供しており、安全な停止方法やその影響についても議論している。一方で、PRの測定と茶の測定は異なる文脈であり、直接的な関連性は確認されていない。また、Scrumの導入により、チームの作業が可視化され、初期のスプリントでは予測性が向上したが、後半では予測性が低下した。これにより、Scrumが未知の作業を知った状態に変換するものではないことが明らかになった。

## 不確実な点・追加確認が必要な点

記事間の食い違いや資料からは断定できない点を以下に示す。まず、記事1と記事3、記事4は「tea break」というキーワードで関連付けられているが、内容の関連性は確認されていない。記事3はランナーのエネルギー源としてカフェインや炭水化物を挙げており、記事4は紅茶の使用量について説明している。両記事は茶に関する測定に焦点を当てているが、ソフトウェア開発におけるPull Request（PR）の測定とは直接的な関連性がない。したがって、PRの測定と茶の測定は異なる文脈であり、両者の関連性は確認されていない。

また、記事2はGitHubのバッジ制度について述べており、PRがマージされた回数や共著コミットの数を基準にしている。一方、記事1はPRごとにフルスイートを実行する必要性やその停止方法について議論している。両記事は同じ「Pull Request」をキーワードにしているが、それぞれ異なる文脈で扱われている。記事2はバッジ制度の測定に焦点を当てており、記事1はCI/CDにおけるテスト実行戦略に焦点を当てている。このため、両記事の関連性は明確ではない。
