# リトライがGitHubを耐障害にしなかった理由

## 結論

リトライ機構が本来の耐障害性を目的としているにもかかわらず、GitHubのインシデントではリトライが逆にサービスの可用性を低下させる原因となった。これは、リトライの設計が不適切だったためであり、リトライを導入する際には予算、ジャイター、バックオフなどの戦略を組み合わせて適切に制御する必要があることを示している。

## テーマ概要

2026年8月17日、GitHubが7時間47分にわたる大規模なインシデントを経験した。このインシデントの主な原因は、Istioのサイドカープロキシが並行処理の制限に達したことで、自動スケーリングがプロキシの過負荷を検知できなかったため、新たなインスタンスがデプロイされなかったことである。これにより、トラフィックが増加し、4つのHAProxyノードが容量限界を超えた結果、ゲートウェイの劣化が発生した。さらに、VSコードのCopilot拡張機能に隠されたバグにより、クライアントがCopilotトークンサービスに対して過剰な認証トークンのリクエストを送信し、トークンサービスの負荷が大幅に増加した。トークンサービスの通常のリクエスト数は1秒あたり7,000〜9,000件で、インシデント中には70,000〜100,000件に急増した。GitHub CTO Vlad Fedorovは、バックエンドエラーがクライアントサイドのリトライループを引き起こし、リカバリ中にトラフィックが増加したと説明した。このインシデントは、リトライが本来の耐障害性を目的としているが、無制限にリトライを行うと、逆にサービスの可用性を低下させる可能性があることを示した。リトライを適切に制御するためには、予算、ジャイター、バックオフなどの戦略が必要であり、これらが組み合わさることで、リトライがサービスに与える影響を制限できる。この出来事は、リトライの設計が慎重に行われなければならないことを浮き彫りにし、現在注目されている。

## 共通して確認できる点

2026年8月17日13:28から21:15UTCにかけて、GitHubが7時間47分にわたるインシデントを経験しました。このインシデントの主な原因は、Istioのサイドカープロキシが並行処理の制限に達したことです。自動スケーリングはホストアプリケーションのメトリクスを監視しており、プロキシの過負荷を検出できなかったため、新しいインスタンスがデプロイされませんでした。これにより、トラフィックが増加し、4つのHAProxyノードが容量限界を超えることとなり、ゲートウェイの劣化が発生しました。また、VSコードのCopilot拡張機能に隠されたバグにより、クライアントがCopilotトークンサービスに対して過剰な認証トークンのリクエストを送信し、トークンサービスの負荷が大幅に増加しました。トークンサービスの通常のリクエスト数は1秒あたり7,000〜9,000件でしたが、インシデント中には70,000〜100,000件に急増し、リカバリ中にさらなる負荷をかけました。GitHub CTO Vlad Fedorovは、バックエンドエラーがクライアントサイドのリトライループを引き起こし、リカバリ中にトラフィックが増加したと説明しました。リトライは本来の耐障害性を目的としているものの、無制限にリトライを行うと、逆にサービスの可用性を低下させる可能性があるため、リトライを適切に制御する必要があります。リトライを制御するためには、予算、ジャイター、バックオフなどの戦略が必要であり、これらが組み合わさることで、リトライがサービスに与える影響を制限できます。リトライは、特定の状況下では自己サービス攻撃を引き起こす可能性があるため、慎重に設計する必要があります。
