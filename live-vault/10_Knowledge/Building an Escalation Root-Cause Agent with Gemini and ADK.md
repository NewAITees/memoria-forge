# GeminiとADKでエスカレーション原因分析エージェントを構築

## 結論

GeminiモデルとADK（Agent Development Kit）の組み合わせにより、企業が顧客サポートにおけるエスカレーションケースの根本原因を自動分析し、コーチングノートの作成を効率化できる技術が実現されている。このアプローチは、手動レビューの負担を軽減し、パターンの見逃しを防ぐことで、スケーラビリティと分析精度の向上を実現しており、企業レベルでの導入が可能である。また、ADKの柔軟な設計は、クラウド環境でのデプロイメントやバッチ処理の実行に適しており、AIエージェントの実装において重要な役割を果たしている。

## テーマ概要

AIによるチケットの自動分析と根拠の特定が求められる企業の業務効率化が背景にある。このテーマでは、GeminiモデルとADK（Agent Development Kit）を組み合わせて、顧客サポートにおけるエスカレーションケースの原因を自動的に特定し、コーチングノートを生成するエージェントの構築が紹介されている。この技術は、人間による手動レビューの負担を減らし、パターンの見逃しを防ぐことで、スケーラビリティと分析精度の向上を目的としている。また、ADKは柔軟な設計により、企業向けのプロダクションレベルでの導入が可能であり、特にGeminiモデルの強力な推論能力を活かした実装が注目されている。

## 共通して確認できる点

複数の記事を分析した結果、AIエージェントの開発とその運用に関連する共通した事実が確認されました。特に、GeminiモデルやADK（Agent Development Kit）の活用が、escalation（エスカレーション）の原因分析や自動化プロセスの改善に向けた重要な技術として位置付けられています。Geminiモデルは、根拠となるテキストを分析し、標準的な分類タックスに従って原因を分類する作業を自動化するための基盤として機能しています。ADKは、柔軟で拡張性の高いフレームワークであり、決定論的および動的なオーケストレーションをサポートし、企業規模での導入に適した環境を提供します。また、これらの技術は、クラウド環境でのデプロイメントや、バッチ処理の実行に適しており、人工的なレビュー作業を補助する効率的な手段として注目されています。さらに、IBM Granite 4.2のような大規模言語モデルの進化は、推論プロセスの高度な制御や、ツール呼び出しの自動化を可能にし、AIエージェントの実装において新たな可能性を開く要素となっています。

## 記事ごとの差分・視点の違い

記事「Building an Escalation Root-Cause Agent with Gemini and ADK」は、Amazonで顧客サポートチームをリードする著者が、GeminiモデルとADKを用いてエスカレーションの根本原因を自動分析するAIエージェントを開発した経総を記述しています。この記事では、手動でのエスカレーションレビューの限界を指摘し、AIによる自動分析の必要性を強調しています。また、ADKフレームワークの柔軟性とモジュール性を強調し、企業規模のデプロイメントに適していると述べています。  

記事「Inside IBM Granite 4.2: Building an Orchestrate-Ready Reasoning App」は、IBM Granite 4.2という大規模言語モデルの機能とアプリケーションアーキテクチャを紹介しています。この記事では、Granite 4.2がハイブリッドな機能をネイティブで統合しており、多段階の推論と高精度なツール呼び出しをサポートしている点を強調しています。また、ローカル環境でのインファレンスや、高性能GPUを用いたスケーリングの両方での実行が可能であることを説明しています。  

記事「GitHub - chatwoot/chatwoot: Open-source live-chat, email support...」は、オープンソースのチャットサポートプラットフォームであるChatwootについて説明しています。この記事では、Chatwootが自己ホスティングが可能であり、AIエージェント「Captain」を用いてチャットサポートを自動化できる点を強調しています。また、アタッチメントの保存に関するドキュメンテーションの不足が指摘されており、自己ホスティング時の課題として取り上げられています。  

記事「Two sites asked my automation to prove it was human. I stopped both times and I want to argue that」は、自動化されたツールが人間であることを証明する必要に追われる状況を記述しています。この記事では、自動化されたプロセスが人間の介入を必要とする場面に遭遇した際の対応と、その背景にある技術的・運用的な課題を論じています。  

記事「Schema Evals for a One-Key Node.js Text Classification API」は、Node.jsを用いたテキスト分類APIの設計と、単一のAPIキーで複数の動作を隠蔽する仕組みについて説明しています。この記事では、APIの設計における柔軟性と、内部の分類契約を保持しながら外部からの呼び出しを可能にするアーキテクチャの重要性を強調しています。

## 深掘り調査で得られた知見

AIを活用したチケット分析の自動化が進展している。Amazonの顧客サービスチームが中心となり、GeminiモデルとADK（Agent Development Kit）を組み合わせて、エスカレーションケースの根本原因を自動的に分析するエージェントを構築した。このエージェントは、チケットの要約を読み込み、標準的な分類体系に基づいて原因を特定し、繰り返しパターンを検出する。また、コーチングノートの作成も自動化しており、人間の作業を補助する。このプロジェクトは、Google Cloud Run上で実行され、CSVファイルをバッチ処理して分析結果を出力するスクリプトも含まれている。さらに、リアルタイムでチケットを分析するため、MCP（Model Control Plane）を介してチケットングシステムと連携する拡張性も検討されている。ADKは柔軟な構造を持ち、デタラメなトリガー源やストレージバックエンドと分離することで、ローカル環境とクラウド環境での運用が可能である。このプロジェクトは2026年7月に公開され、同フレームワークを用いたセキュリティアラートのトリガーも2026年8月に公開されている。また、IBM Granite 4.2は、多段階推論とXMLベースのツール呼び出しをネイティブでサポートし、リソース制約のあるエッジデバイスでも動作可能である。Chatwootは、オープンソースのチャットサポートプラットフォームであり、自己ホスティングが可能で、AIエージェントCaptainを搭載してチャットサポートを自動化する。ただし、アタッチメントの保存に関するドキュメンテーションの不足が指摘されている。また、自動化されたプロセスが人間の検証を必要とするケースも増えている。一部のウェブサイトでは、自動化されたツールが人間であることを証明する必要があると要求しており、これは自動化プロセスの信頼性やセキュリティへの関心が高まっていることを示している。

## 不確実な点・追加確認が必要な点

記事間の食い違いや、資料からは断定できない点を具体的に書くと、以下の通りです。

記事1では、GeminiモデルとADK（Agent Development Kit）を用いて、顧客サポートにおけるエスカレーションの根本原因を自動分析するAIエージェントが構築されていることが明記されています。このエージェントは、Google Cloud Run上で稼働し、CSVファイルからのバッチ処理をサポートしており、実際のチケットングシステムとの連携も検討されています。また、ADKフレームワークは、決定論的および動的なオーケストレーションをサポートし、企業レベルでの展開に適しているとされています。

一方で、記事2では、IBM Granite 4.2という大規模言語モデルが紹介されており、これはハイブリッドな機能をネイティブで統合した企業向けのオープンソースモデルです。Granite 4.2は、多段階の推論（Chain-of-Thought）とXMLベースのツール呼び出しを組み合わせており、リソース制約のあるエッジハードウェアや高性能GPUを用いた展開が可能となっています。また、Granite 4.2は、IBM Researchによって2026年8月25日にリリースされ、Apache License 2.0で公開されており、研究および商業用途での無料使用が許可されています。

記事3のChatwootは、オープンソースのチャットサポートプラットフォームで、自己ホスティングが可能であることが述べられています。アタッチメントの保存に関しては、ドキュメンテーションに警告が含まれていない点が指摘されており、自己ホスティングでの運用においてアタッチメントの保存に関する問題が生じる可能性があるとされています。また、ChatwootはAIエージェントであるCaptainを搭載しており、チャットサポートを自動化する機能を備えています。

記事4では、自動化されたプロセスが人間による確認を求めるケースが発生した際、そのプロセスを停止した経緯が記述されています。これは、サイトが自動化されたプロセスを人間として確認を求めていることを示しており、そのようなケースは、現時点で明確な理由が示されていません。

記事5では、Node.jsを用いたテキスト分類APIの設計について述べられており、1つのAPIキーが複数の動作を隠蔽していることや、モデルルーティングやチャット完了処理の扱いについての設計が説明されています。ただし、具体的な実装やデプロイメントの詳細は記述されていません。
