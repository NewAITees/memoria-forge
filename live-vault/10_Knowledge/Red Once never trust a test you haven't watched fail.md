# テスト駆動開発における信頼性の確保方法

## 結論

テスト駆動開発（TDD）において、テストが失敗する瞬間を人間が確認しない場合、そのテストは信頼性を欠く可能性があるという主張は、逆変異テストやCI/CDパイプラインでのテスト失敗の問題と密接に関連しており、テストの有効性を評価する上で重要な指針となる。特に、ローカルでのテストが通るがCI環境で失敗する現象は、ビルドグラフやプロジェクト参照の影響を示しており、テストの信頼性を確保するためには、テストが実際にコードの動作を検出できるかどうかを確認する必要がある。

## テーマ概要

テスト駆動開発（TDD）における「Red Once: never trust a test you haven't watched fail」というテーマは、テストが失敗する瞬間を人間が確認していない場合、そのテストは信頼できないという考え方を示しています。この考えは、テストがコードの実際の動作を正確に反映していない可能性があることを指摘しており、逆変異テスト（reverse mutation testing）などの手法を通じてテストの有効性を評価する必要があるとされています。このテーマは、テストが常に緑（成功）になる場合、それはテストがコードの実際の動作を正確に反映していないことを意味する可能性があるため、現在注目されています。また、CI/CDパイプラインでのテスト失敗や、ローカルでのテストが通るがCI環境では失敗するといった問題も関連しており、テストの信頼性とビルドグラフの問題が重要なテーマとなっています。

## 共通して確認できる点

テストの信頼性に関する議論は、複数の記事で共通して取り上げられている。特に「Red Once: never trust a test you haven't watched fail」というフレーズは、テストが失敗する瞬間を人間が確認していない場合、そのテストは信頼できないという考え方を示している。テスト駆動開発（TDD）では、テストを書いた後にコードを書くことが一般的だが、テストが失敗する瞬間を確認しないと、テストの有効性が疑われる。逆変異テスト（reverse mutation testing）は、テストが実際に何を検出できるかを評価するための手法であり、テストが失敗する瞬間を確認しないと、テストの有効性が疑われる。テストが失敗する瞬間を確認するためには、テストを書いた後にコードを変更し、テストが赤（失敗）になるかどうかを確認する必要がある。

また、テストがローカルでは通るが、CI環境で失敗するという問題も指摘されている。これは、プロジェクト参照がビルドグラフに与える影響を理解する上で重要な例であり、テストプロジェクトがブラウザアプリケーションのヘッドを参照することで、CI環境での評価が失敗する場合がある。テストが実際に必要な最小限の依存関係に依存することで、アーキテクチャ上の問題を回避できる。この問題は、ローカルでのテストが通るが、CI環境での失敗を引き起こすため、ビルドグラフの問題である。

さらに、Flaky tests（不安定なテスト）の問題も取り上げられている。Flaky testsは、アプリケーションやテストコードの変更なしに、結果が不一致になるテストであり、CI/CDパイプラインの信頼性に悪影響を及ぼす。タイミング問題や共有データ、環境差異などが主な原因とされ、テスト結果の信頼性が低下し、リランズの増加や潜在的なリグレッションの発見が遅れる可能性がある。これらの問題に対処するためには、確定的な検出方法や管理戦略が求められている。

## 深掘り調査で得られた知見

テスト駆動開発（TDD）における「Red Once」の原則は、テストが失敗する瞬間を人間が確認していない場合、そのテストは信頼できないという考え方を示しています。記事1では、テストが常に緑（成功）になる場合、それはテストがコードの実際の動作を正確に反映していないことを意味する可能性があると指摘しています。逆変異テスト（reverse mutation testing）は、テストが実際に何を検出できるかを評価するための手法であり、テストが失敗する瞬間を確認しないと、テストの有効性が疑われるとしています。テストが失敗する瞬間を確認するためには、テストを書いた後にコードを変更し、テストが赤（失敗）になるかどうかを確認する必要があります。

また、記事3では、ローカルではテストが通るがCI環境で失敗する問題が挙げられています。これは、プロジェクト参照がアセンブリの利用だけでなく、ビルドグラフ、ターゲット、ワークロード、生成されたアセット、プロパティに敏感な挙動なども含むためです。CI環境では、テストプロジェクトがブラウザアプリケーションのヘッドを参照することで、ブラウズSDKが期待するタスクやターゲットが提供されないため、評価が失敗する可能性があります。この問題は、プロジェクト参照がビルドグラフに与える影響を理解する上で重要な例として挙げられています。

さらに、記事5では、flaky test（不安定なテスト）の問題が取り上げられています。flaky testは、アプリケーションやテストコードが変更されないにもかかわらず、テストが不一致した結果を返す問題で、CI/CDパイプラインの信頼性を低下させます。タイミングの問題や共有データ、環境の違いなどが主な原因とされており、これらの問題を解消するためには、デターミニスティックなウェイト、テストの隔離、検出戦略の導入などが挙げられています。

## 不確実な点・追加確認が必要な点

記事間では、テストの信頼性に関する考え方や、テストが失敗する瞬間を確認する必要性について一致しているが、具体的な背景や文脈には違いがある。例えば、「Red Once: never trust a test you haven't watched fail」では、テスト駆動開発（TDD）のプロセスにおいて、テストが失敗する瞬間を人間が確認しないとそのテストの有効性が疑われるという主張がなされている。これは、テストがコードの実際の動作を正確に反映していない可能性を指摘している。一方、記事「AGreenLocalTestCanHideaBrokenProjectGraph」では、テストがローカルでは通るがCI環境で失敗する問題が取り上げられており、これはプロジェクト参照やビルドグラフの問題であるとされている。このように、テストの失敗が原因となる問題の種類が異なっている。

また、「Flaky Test Guide (2026): Causes, Examples, And Fixes」では、テストが不確実な結果を返す「flaky test」の原因や対策が具体的に説明されており、時間的な問題、共有データ、環境の違いなどが挙げられている。これは、テストの信頼性を確保するための技術的な対策を示しているが、テストが失敗する瞬間を確認するという主張とは異なるアプローチである。したがって、各記事が扱う文脈や背景には違いがあり、断定的な結論を出すことは難しい。
