# クライアント提供テナントIDの信頼は禁物

## 結論

クライアントが提供するテナントIDを信頼してはいけないという原則は、多租户システムのセキュリティ設計において不可欠であり、認証とテナント分離の区別を明確にすることが重要です。サーバー側でテナントを解決し、クライアントの提供を検証する必要があり、IDORのようなリスクを回避するためには、データベースやクエリレベルでのテナント分離が求められます。OAuthスコープや権限の仕組みは、認証の代替として使われてはならないため、リソースレベルでのアクセス制御が適切に実装される必要があります。

## テーマ概要

多租户システムにおいて、クライアントが提供するテナントIDを信頼してはいけないという問題が注目されています。認証はユーザーの身分を確認するものであり、テナントを操作できる権限を示すものではありません。クライアントがテナントIDを指定できると、不正に他のテナントのデータにアクセスするリスクが生じるため、サーバー側でテナントを解決し、クライアントの提供を検証する必要があります。この問題は、IDOR（インデックスベースのアクセス違反）の一形態として扱われ、データベースやクエリレベルでのテナント分離が求められています。また、OAuthスコープや権限の仕組みが適切に使われていない場合、セキュリティリスクが生じる可能性があるため、適切な認証と authorization の設計が重要となっています。

## 共通して確認できる点

クライアントが提供するテナントIDを信頼してはいけないという点は、複数の記事で一致しています。認証はユーザーの身分を確認するものであり、どのテナントを操作できるかを示すものではありません。そのため、サーバー側でテナントを解決し、クライアントが提供したテナントIDを検証する必要があります。例えば、Dev.toの記事では、APIがリクエストボディやクエリ文字列からテナントIDを取得し、ユーザーが認証されている場合にそのテナントのデータを読み込むというパターンが挙げられており、これが認証の誤用として指摘されています。また、LinkedInの記事では、バックエンドがクライアントから受け取ったテナントIDを信頼すると、セキュリティ上の重大な問題が生じる可能性があると説明されています。このような状況では、認証されたプリンシパルからテナントIDを取得するべきであり、クライアントが提供する値を直接信頼してはいけないという原則が共有されています。

## 記事ごとの差分・視点の違い

記事「Never trust a client-supplied tenant ID」では、クライアントが提供するテナントIDを信頼すべきではないという基本的な原則を強調しており、認証とテナント分離の違いを明確にしている。一方、「Authentication Is Not Tenant Isolation」では、認証がテナントの分離を保証しないことを詳しく説明し、特に金融プラットフォームにおけるデータ境界の重要性を指摘している。また、「Scopes for OAuth apps - GitHub Docs」では、OAuthスコープの役割と限界を説明し、スコープが認可モデルの代替として使われることの危険性を示している。さらに、「Using OAuth 2.0 scopes vs. permissions for app authorization」では、OAuthスコープがアプリケーションの権限を表すものではないという論点を掘り下げ、適切な権限管理が必要であることを強調している。最後に、「The Hotel Upgrade Hack: Mass Assignment... - DEV Community」では、Mass Assignmentの脆弱性を例に挙げて、クライアントが提供するデータを直接モデルにバインドする危険性を説明しているが、これはテナント分離の問題とは直接関係がない。

## 深掘り調査で得られた知見

クライアントが提供するテナントIDを信頼しないという原則は、多租户（マルチテナント）アーキテクチャにおいて非常に重要です。認証プロセスはユーザーの身分を確認するものであり、どのテナントに対して操作権限があるかを示すものではありません。そのため、サーバー側でテナントを解決し、クライアントが提供したテナントIDを検証する必要があります。例えば、Dev.toの記事では、APIがリクエストボディやクエリ文字列からテナントIDを取得し、認証済みユーザーがそのテナントのデータを読み込むというパターンが指摘されており、これはIDOR（インデックスに基づくアクセス違反）の一種としてリスクが示されています。

また、LinkedInの記事では、JWT（JSON Web Token）が有効であっても、テナントIDをクライアントが提供する場合、システムのセキュリティに重大な問題が生じる可能性があると説明されています。認証はユーザーの身分を確認するものであり、テナントのデータにアクセスできるかどうかは別の authorization（認可）プロセスで判断されるべきです。この区別が曖昧になると、認証が成功しても、不正に他のテナントのデータにアクセスする可能性が生じるため、セキュリティ上の脆弱性が発生します。

OAuth 2.0におけるスコープ（scopes）は、アプリケーションがユーザーのアカウントに対してアクセスする権限を指定するためのメカニズムですが、これらはアクセス制御のための代替手段としては不十分です。GitHubのドキュメントでは、OAuthアプリケーションではなく、GitHub Appsを使用することで、より細かい権限管理が可能であると説明されており、スコープは権限の代わりに使用すべきではありません。また、Asertoの記事では、スコープはアプリケーションの権限を決定するためのメカニズムとして適切ではないと指摘されており、リソースレベルの認可が実装されるべきであるとされています。

これらの情報は、多租户アプリケーションにおけるセキュリティ設計において、クライアントが提供するテナントIDを信頼しないという原則が重要であることを示しています。テナントの分離やデータの境界を守るためには、サーバー側での制御が不可欠であり、クライアントの入力に依存してはならないという点が強調されています。

## 不確実な点・追加確認が必要な点

記事間では、クライアントが提供するテナントIDを信頼しないという共通の警告が示されているものの、具体的な実装方法やセキュリティリスクの詳細な説明には違いがある。例えば、Dev.toの記事では、テナントIDがクライアントから提供される場合、IDOR（インデックスに基づくアクセス違反）の一種としてリスクが指摘されており、データベースやクエリレベルでのテナント分離が提案されている。一方、LinkedInの記事では、認証とテナント分離の違いを強調し、トークンの検証とテナントの所有権の確認が分離されていると説明されている。また、OAuthスコープに関する記事では、スコープが認証の代替として使われることを強く否定しており、リソースレベルでのアクセス制御が求められている。これらの記事は、テナントIDの信頼性に疑問を抱く点では一致しているが、具体的な対策や実装の詳細については異なる視点から説明されている。そのため、一概にどの記事の内容を正しいと断定することはできず、各記事の主張を個別に検討する必要がある。
