# 特定ボードの再現性低下によるアウトagesスコア不成立の証拠不足

## 結論

このテーマで最も重要な判断は、特定のボードが再現性の低下としてアウトagesをスコア付けなかったという主張は、証拠の不十分さから成立していないという点である。検証プロセスにおいて、拒否サイトが不完全であるため、真の不具合が検出されない可能性があり、その限界が明確に指摘されている。

## テーマ概要

このテーマは、特定のボード（評価システム）が再現性の低下（レグレッション）としてアウトages（障害）を記録していないという主張と、その主張を裏付ける証拠が不足しているという問題を扱っています。記事では、主張を検証するための「証拠バンドル」を作成し、その検証プロセスを説明していますが、結果として証拠が不十分であることが明らかになっています。また、このテーマは、評価システムの信頼性や証拠の妥当性に関する議論を引き起こしており、特に技術的な評価や機械学習モデルの検証において重要な課題として注目されています。

## 共通して確認できる点

複数の記事では、特定のボードがリグレッションとしてアウトagesをスコア付けなかったという主張がなされ、その証拠としての検証プロセスについて議論されている。記事1では、自身の verifier が「clean」と呼ぶ証拠バンドルを forge し、拒否サイトでの変異を試みた結果、4バイトの最も安価な偽造が生存したと報告されている。また、SPEC.md には 39 の規範的義務があり、そのうち 37 が MUST、2 が MUST NOT であるが、どの義務にも拒否サイトがマッピングされていないという事実が指摘されている。このため、規範的義務が拒否サイトにマッピングされていない場合の数は測定されていない状態である。

また、記事2では、2026年9月30日に Apple のサービスがダウンし、Apple TV が利用不能になったなどの情報が記載されている。同様に、Spotify や DoorDash、Anthropic の Claude なども同日にシステムダウンが発生している。これらの情報は、特定のボードがリグレッションとしてアウトagesをスコア付けなかったという主張と直接的な関連性は見られないが、一般的なサービスのダウンタイムに関する事実として記録されている。

記事3では、1つのhung API callが1,000回のベンチマークを中断し、数時間の完了した作業を破棄したという事例が紹介されている。この問題に対して、5段階の修正策が提示されており、特に「1つのhung callを第一級の失敗状態として扱う」ことが重要視されている。この修正策は、モデルや機械の性能向上ではなく、インフラストラクチャの信頼性向上に焦点を当てている。

記事5では、ツールの評価結果が信頼性が低く、ユーザーが自分の判断を過信してしまうリスクがあると指摘されている。特に、入力の長さに依存する構造の読み取りがツールの主要な制限であり、短い文章と全体の文章では評価が大幅に変化する可能性がある。このため、ツールの制限を明示することで信頼が得られ、ユーザーがブラックボックスに依存するのを防ぐことが重要だとされている。

## 記事ごとの差分・視点の違い

記事「My board never scored an outage as a regression. My evidence couldn't prove it」では、作者自身が自分のボードが回復障害を再現していないことを証明しようとしたが、証拠が不十分だったことを述べている。一方、記事「Outage| TeckDeck.io」では、複数のサービスがダウンした事例が紹介されており、特定のサービスの障害が報告されている。記事「One Hung API Call Used to Kill My 1,000-Run Benchmark」では、1つのAPI呼び出しが1,000回のベンチマークを破壊したという経験が共有され、その問題の解決策が述べられている。記事「HumanBenchmark」では、ツールの評価が入力の長さに強く依存しており、短い文章と全体の文章では評価が大幅に変化する可能性があるという問題点が指摘されている。最後に、「Why we publish the cases where our tool performs worst」では、ツールの性能が悪かった場合でもそれを公開することで、ユーザーが信頼できると感じることを説明している。各記事はそれぞれ異なる視点から、技術的な問題やツールの限界について語っている。

## 深掘り調査で得られた知見

深掘り調査では、「My board never scored an outage as a regression. My evidence couldn't prove it」という主張が、技術的な検証プロセスにおける信頼性と限界についての議論を引き起こしていることが明らかになった。記事1では、検証者が「clean」と判断する証拠を forge（偽造）し、その耐性をテストする試みが行われた。具体的には、検証者が拒否すべき場所を変異させ、どの程度の変異が検出されないかを数えた。その結果、最も安価な偽造でも4バイトの変異で検出されなかった例が確認された。このプロセスでは、検証者が拒否する場所が不足しているため、真の不具合が検出されない可能性があることが指摘されている。

また、SPEC.mdに記載されている39の規範的義務（37のMUST、2のMUST NOT）に対して、どの義務にも拒否場所が割り当てられていないという事実も明らかになった。これは、検証プロセスの欠陥として、未検出の義務が存在することを示している。さらに、検証プロセスの信頼性を高めるためには、検証対象の範囲を明確にし、検証結果の透明性を確保することが求められている。

記事3では、1つのAPI呼び出しのハングが1,000回のベンチマークを破壊した事例が紹介されている。この問題は、検証プロセスの信頼性に直結しており、部分的なスキャンが完了したかのように見え、誤った結果を生じる可能性がある。その解決策として、タイムアウトの設定、非再試行可能な分類、クォラント、トラジェクトリーベースのトークン制限、シャットダウン時のキャンセル、モデルごとの価格設定など、5つの対策が提示されている。この事例は、検証プロセスの信頼性を高めるためには、単なるモデルの改善ではなく、検証環境の強化が不可欠であることを示している。

## 不確実な点・追加確認が必要な点

記事間の食い違いや、資料からは断定できない点を具体的に述べると、以下の通りです。  

まず、記事1では、あるボードがアウトagesとしてのレグレッションを記録しなかったという主張を、証拠の偽造を通じて検証しようとしたが、その証拠は不十分であり、証拠の限界が指摘されています。具体的には、検証者が拒否するサイトを変異させ、どの変異が生き残ったかを数えたが、その結果は限定的であり、どの規約にも対応していない義務（spec obligations）が存在することも明確ではありませんでした。このため、主張を証明できなかったと結論付けています。  

一方で、記事2では、Outageに関する情報が掲載されていますが、具体的な内容は不明です。また、記事3では、1,000回の評価を実行したが、1つのAPI呼び出しが原因で失敗し、結果が破損したという経験が述べられています。この記事では、失敗の原因がデータではなくランナー（実行環境）にあると指摘しており、その修正方法についても述べています。  

記事4については、HumanBenchmarkというサイトのダッシュボードが掲載されているのみで、具体的な内容は不明です。記事5では、ツールの性能が最悪なケースを公開している理由について説明しており、ツールの評価が入力の長さに依存することや、信頼性の低さが問題であると述べています。  

これらの記事は、それぞれ異なるテーマや背景を持つため、直接的な関連性は低いです。特に、記事1と他の記事では、アウトagesやレグレッションに関する具体的な事例やデータが不足しており、断定的な結論を導くことはできません。また、記事1では、 SPEC.md に記載されている規約の数や、それらに紐づく拒否サイトの数についても明確な情報が得られていません。そのため、これらの点については、さらなる調査や情報収集が必要です。
