# TechEmpowerベンチマークのアーカイブとAPI性能向上の課題

## 結論

TechEmpower Framework Benchmarksのアーカイブにより、バックエンド技術の性能比較に使われていた主要なベンチマークが消失した。その結果、代替としてHttpArenaが登場しているが、まだTechEmpowerのカバー範囲に達していない。また、APIのパフォーマンス向上には、言語選択だけでなく、キャッシュ、データベース最適化、ネットワーク改善などの設計が重要であることが明確になった。

## テーマ概要

TechEmpower Framework Benchmarksが2026年3月にアーカイブされたことで、バックエンド技術の性能比較に使われていた主要なベンチマークが消失した。このベンチマークは12年間、技術選定の基準として使われていたが、結果が実際のアプリケーションに反映されていないことや、テスト環境の変化がなかったことなどが原因で信頼性が低下した。その結果、新たなベンチマークとしてHttpArenaが登場しているが、まだTechEmpowerのカバー範囲に達していない。この出来事は、バックエンド技術の選定において、単に言語やフレームワークの性能だけではなく、実際のアプリケーション環境や設計が重要であることを示している。また、Vercelのようなサーバーレス環境でのAPIホスティングが注目され、キャッシュやレート制御といった実装上の課題が浮き彫りとなった。これらの背景から、バックエンドの性能評価と実装の現状が注目されている。

## 共通して確認できる点

TechEmpower Framework Benchmarksは、2014年から2026年3月まで、バックエンド技術の性能比較のための主要なベンチマークとして使われていた。しかし、2026年3月にアーカイブされ、その理由は、テストの結果が実際のアプリケーションとはかけ離れており、信頼性が低下していたためである。特に、テストプラットフォームが数年間変化しなかったことや、結果がハーキスによって制限されていたこと、低レベルの最適化を許容していたことが指摘されており、これらの問題はベンチマークの信頼性を損なっていた。最終的なラウンドでは、ASP.NET Core、Fiber（Go）、Actix（Rust）、Spring（Java）、Express（Node.js）などのフレームワークがそれぞれの性能を示し、Microsoftがプロジェクト中に56コアのサーバーを提供したことで、結果が過去のラウンドと比較して大幅に変化している。そのため、結果の絶対値は過去のラウンドと直接比較できない。代替として、HttpArenaという新しいプロジェクトがHTTP/2やWebSocketのサポートを含めてベンチマークの再構築を試みているが、まだTechEmpowerのカバー範囲に匹敵するまでには至っていない。また、APIのパフォーマンスにおいて、言語自体の影響は限定的で、主にデータベースの未インデックス化、N+1パターン、外部サービスへの同期呼び出し、キャッシュの欠如など、他の要因がパフォーマンスに大きな影響を与えている。

## 記事ごとの差分・視点の違い

記事「Go vs Node.js vs Java vs Python: Which Backend Is Fastest?」では、TechEmpower Framework Benchmarksの結果をもとに、バックエンド技術のパフォーマンス比較を行っている。このベンチマークは2026年3月にアーカイブされ、結果が現実的なアプリケーションと乖離していたため、その理由が強調されている。また、言語選択がAPIの遅さの主因ではないと指摘し、実際のパフォーマンスを左右する要因が他の要素にあることを示している。

記事「The benchmark everyone cited for "fastest backend" was archived in March, and the reason is the interesting part」は、TechEmpowerベンチマークがアーカイブされた背景とその理由を掘り下げている。特に、テスト環境が長期間変化せず、結果がフレームワークではなくハーネスで制限されていた点が強調されており、ベンチマークの信頼性への疑問を提起している。

記事「Hosting your API on Vercel | Vercel Knowledge Base」は、Vercelが提供するAPIホスティングの仕組みとその利点を説明しており、サーバーレス環境での高可用性とスケーラビリティ、キャッシュ機能、および冷起動の軽減策について述べている。これはVercelが提供する技術的サポートの側面を強調している。

記事「7 Ways to Make Your API Faster- DEV Community」は、APIの高速化に向けた具体的な改善策を提示しており、キャッシュの導入、データベースの最適化、ネットワークの改善など、実践的なアプローチを紹介している。これは、APIのパフォーマンスを向上させるための実装例としての側面が強調されている。

## 深掘り調査で得られた知見

TechEmpower Framework Benchmarks は、バックエンドの性能比較において長年使われてきた基準でしたが、2026年3月にアーカイブされました。その理由は、ベンチマークのテストプラットフォームが長期間変化しなかったことや、結果がハーキスによって制限されていたこと、また低レベルの最適化が許可されていたことが挙げられます。これらの問題により、結果は現実的なアプリケーションとは程遠く、信頼性が低下していました。最終ラウンドでは、ASP.NET on C# が約610,000リクエスト/秒、Fiber on Go が約338,000リクエスト/秒、Actix on Rust が約320,000リクエスト/秒、Spring on Java が約244,000リクエスト/秒、Express on Node が約78,000リクエスト/秒と記録されました。ただし、マイクロソフトがプロジェクト途中で56コアのサーバーを提供し、ネットワーク帯域幅を40Gbpsに設定したことにより、結果は過去のラウンドと比較して大幅に異なっています。これにより、絶対的な数値は過去のラウンドとは比較できません。代替プロジェクトとして HttpArena が HTTP/2 や WebSocket のサポートを含めて TechEmpower の代替を目指していますが、まだ同等のカバレッジは達成していません。

Vercel は、サーバーレス環境での API ホスティングに適しており、高可用性とスケーラビリティを提供しています。しかし、サーバーレスモデルでは、各リクエストごとに新しいインスタンスが作成されるため、インメモリキャッシュやレート制御に影響を与える可能性があります。ローカル環境ではキャッシュが永続的に保持される一方、Vercel ではインスタンスがシャットダウン後にキャッシュが初期化されるため、キャッシュの効果が低下する場合があります。また、Vercel は冷起動を最小限に抑えるためのバイナリキャッシュやプリウォーム機能を提供していますが、特定のケースでは効果が限定的です。Express アプリケーションを Verc,el にデプロイする際には、`app.listen()` の使用を避け、`module.exports` で Express アプリケーションをエクスポートする必要があります。さらに、`vercel.json` ファイルの `builds` プロパティが古くなったため、削除が必要な場合があります。Vercel は API ルートの設定が間違っている場合、警告を表示し、API ルートが動作しない可能性があります。また、Vercel は HTTP レスポンスのストリーミングをサポートし、リアルタイム AI インフェレンスや部分的なページレンダリングに適しています。さらに、Vercel は複数のリージョン間でのフェイルオーバーをサポートし、高可用性を提供しています。

API の高速化には、具体的な問題点を特定し、それに応じた最適化を行うことが重要です。キャッシュの使用は、短い TTL を採用することで、大量のリクエストを効率的に処理し、データベースへの負荷を大幅に減らすことができます。ただし、データの新鮮さが求められる場合、キャッシュ無効化の複雑性が生じるため、慎重に設計する必要があります。データベースの最適化には、インデックスの導入や接続プールの使用が有効で、これによりデータベースへのアクセス時間を短縮できます。また、HTTP/2 や HTTP/3 の導入により、ネットワークレイテンシーが削減され、全体的な API 性能が向上します。リクエストの圧縮や、必要なデータのみを送信するといった技術も、API の応答速度を向上させる手段として有効です。

## 不確実な点・追加確認が必要な点

記事間では、バックエンド性能のベンチマークに関する情報がいくつかの矛盾や曖昧な点を示しています。記事1では、TechEmpower Framework Benchmarksが2026年3月にアーカイブされ、その理由としてベンチマークの結果が現実のアプリケーションとずれていたことが挙げられています。これは、テストプラットフォームの変更がなかったことや、結果がハルネスによって制限されていたことなどが原因とされています。一方で、記事2では、「fastest backend」のベンチマークが3月にアーカイブされたことが述べられていますが、その理由については具体的な説明が不足しています。また、記事4はVercelでのAPIホスティングについて説明しており、サーバーレス環境の特徴やその利点を述べていますが、ベンチマークのアーカイブと直接的な関連性は示されていません。これらの資料から断定することはできず、それぞれの記事が提示する情報は独立して理解する必要があります。
