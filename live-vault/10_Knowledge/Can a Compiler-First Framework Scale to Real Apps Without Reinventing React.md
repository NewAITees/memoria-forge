# コンパイラファーストフレームワークが実アプリにスケール可能か

## 結論

コンパイラファースト型フレームワークが現実的なアプリケーションにスケール可能かどうかは、フレームワークがアプリケーションに必要な機能を十分にサポートできるかどうかにかかっています。Kudzuのようなフレームワークは、Reactの構文を維持しつつ、仮想DOMやハイドレーションを必要とせず、静的なページを極めて小さなサイズにすることが可能ですが、大規模なアプリケーションには共有状態管理、認証、リアルタイム更新など、本格的な機能を提供する必要があります。一方、Vue.jsベースのアプリケーションはTauriやCapacitorを活用して、デスクトップ、Android、Webで統合的に動作する単一のUIを実現しており、その柔軟性と実用性が注目されています。

## テーマ概要

コンパイラファースト型フレームワークが現実的なアプリケーションにスケール可能かどうかというテーマは、Web開発におけるフレームワークの設計哲学と実用性のバランスを問うものです。このテーマは、Reactのような仮想DOMやハイドレーションを必要としない、コンパイラ中心のアプローチを採用したフレームワーク（例：Kudzu）が、大規模で長期運用可能なアプリケーションを構築できるのかどうかを議論しています。その背景には、コンパイル時にアプリの状態やイベントを分析し、必要なJavaScriptのみを出力することで、パフォーマンスやバンドルサイズの最適化が可能になるという技術的利点があります。しかし、一方で、このようなアプローチが実際のアプリケーションに必要な機能（例：共有状態管理、非同期データ取得、認証、リアルタイム更新など）を十分にサポートできるかが課題となっています。このテーマは、今注目されている理由は、Webアプリケーションの構築方法の革新と、既存フレームワークの限界を超える可能性を問う点にあります。

## 共通して確認できる点

複数の記事から共通して確認できた事実として、コンパイラファースト型フレームワークの設計において、Reactのような仮想DOMやハイドレーションを必要としないことで、静的ページのサイズを極限まで小さくすることが可能であることが挙げられる。また、このようなアプローチが大規模なアプリケーションの構築に適切かどうかは、フレームワークがリアルなアプリケーションに必要な機能（例えば、共有アプリケーションステート、非同期/サーバーからのデータ取得、ローディング・エラーステート、キャッシュ無効化、楽観的ミューテーション、複雑なフォーム、ネストされたルーティング、認証・権限管理、リアルタイム更新、大規模なリストと仮想化、エディタやチャート・マップのサポート、コードスプリット、長寿命のアプリケーションステートなど）を十分にサポートできるかが鍵となる。一方で、フレームワークがこれらの機能を扱う際に、フレームワーク固有の機能を過剰に追加せず、アプリケーションが実際に必要な能力に焦点を当てた設計が求められている。また、現状の技術動向として、Vue.jsベースのアプリケーションをデスクトップ、Android、Webで統合的に実行する方法として、TauriとCapacitorの使用が挙げられ、これにより一つのUIコードベースで複数のプラットフォームをサポートすることが可能である。さらに、C++とWebView2を組み合わせることで、軽量かつ効率的なWindowsデスクトップアプリケーションの構築が可能となり、Electronのようなブラウザエンジンをバンドルする必要がないという利点がある。

## 記事ごとの差分・視点の違い

記事ごとの立場や強調点、論点の違いは以下の通りです。

記事「Can a Compiler-First Framework Scale to Real Apps Without Reinventing React?」では、Kudzuというコンパイラファースト型のフレームワークが、Reactを再実装せずに大規模なアプリケーションを開発できるかという問いを提起しています。この記事では、Kudzuが静的サイトコンパイラとしての機能を超えて、リアルなアプリケーションフレームワークとして成長できるかが焦点です。著者は、Kudzuがアプリケーションの複雑な状態管理や認証、リアルタイム更新など、本格的なアプリケーションに必要な機能を扱えるかどうかを問うています。また、Kudzuがフレームワーク特有の機能を過剰に追加せず、少数の強力なプリミティブで構成されることを推奨しています。

記事「Ask HN: How does one build large front end apps without a framework?」では、フレームワークを使わずに大規模なフロントエンドアプリケーションを開発する方法を探っています。この記事では、ネイティブモジュールとES6クラスを使用し、各機能（カシーラー、モーダル、フォームなど）を個別のモジュールとして構築する方法が提案されています。著者は、フレームワークに依存せず、アプリケーションをライブラリとして構築する必要があると強調しています。このアプローチは、フレームワークの制限を回避し、柔軟なアプリケーション設計を可能にします。

記事「One Vue app, three homes: desktop with Tauri, Android with Capacitor and the web」では、Vue.jsベースのアプリケーションをデスクトップ、Android、Webで共通して実行可能な単一のUIとして構築する方法が紹介されています。TauriとCapacitorの使用により、同じコードベースで複数のプラットフォームにアプリケーションを展開できることが強調されています。著者は、それぞれのプラットフォームに合わせたネイティブツールチェーンの利用や、OAuthリダイレクトなどの実装における課題についても述べています。

記事「#vuejs articles | Hashnode」では、Vue.jsの使用がWeb開発者にとってデスクトップおよびモバイルアプリケーション開発にも適していることを示しています。この記事では、Vue.jsをベースにしたアプリケーションが、ネイティブなデスクトップアプリやモバイルアプリに展開可能であるための技術的アプローチが紹介されています。また、CIマトリクスやOAuthリダイレクトなどの実装における注意点も説明されています。

記事「Why I Built a Windows Desktop App with C++ + WebView2 Instead of Electron」では、ElectronではなくC++とWebView2を組み合わせてWindows用のデスクトップアプリを開発した理由が説明されています。この記事では、Electronが持つ Chromium のバンドルにより、メモリ使用量と起動時間に課題があり、それが常に実行されるアプリケーションに適していないとされます。WebView2は既にインストールされている Edge エンジンを使用するため、軽量で効率的なアプリケーション構築が可能だとされています。著者は、WebView2とC++の組み合わせが、Windowsプラットフォームでネイティブなアプリケーション開発に適していると結論付けています。

## 深掘り調査で得られた知見

深掘り調査では、コンパイラファースト型フレームワークが現実的なアプリケーション開発に適切かどうかに関する議論が明らかになりました。Kudzuというフレームワークは、Reactの構文を維持しつつ、ReactやVDOM、ハイドレーションをデフォルトで使用しないことで、静的なページを極めて小さなサイズにしています。しかし、このアプローチが大規模なアプリケーションにも拡張可能かどうかは不明です。Kudzuが大規模なアプリケーションに適応するためには、アプリケーションの共有状態管理、非同期/サーバーからのデータ取得、ロードとエラーステート、キャッシュ無効化、楽観的変更、複雑なフォーム、ネストされたルーティング、認証と権限、リアルタイム更新、大規模なリストと仮想化、編集機能、チャートや地図、コードスプリット、長寿命のアプリケーション状態などをサポートする必要があります。Kudzuがこれらの機能を効果的に扱うことができない場合、静的なサイトコンパイラに近づく可能性があります。また、Kudzuはフレームワーク特有の機能ではなく、アプリケーションに必要な基本的な能力を提供するべきです。

一方、Vue.jsベースのアプリケーションは、TauriやCapacitorといったツールを活用することで、デスクトップ、Android、Webのすべてのプラットフォームで動作する単一のUIとして構築されています。TauriはRustベースで、デスクトップアプリケーションの構築に適しており、CapacitorはAndroidアプリケーションの構築に適しています。WebView2はWindows 11でサポートされており、それ以前のバージョンではインストーラーをバンドルする必要があります。OAuthリダイレクトはブラウザでは簡単ですが、パッケージ化されたアプリケーションではカスタムスキームやディープリンクを使用する必要があります。Vue.js + Tauri + Capacitorは、Web開発者にとってデスクトップおよびモバイルアプリケーションを開発するための非常に合理的な方法です。

また、yyzToolsというWindows向けの生産性ツールは、C++ (Win32) + WebView2 + Alpine.js + Viteを採用し、Electronを避けました。Electronは Chromium をバンドルしており、メモリ使用量と起動時間のコストが高く、常に実行されているアプリケーションには不向きです。WebView2は既にインストールされているEdgeエンジンを使用するため、軽量で効率的なアプリケーションを構築できます。ただし、WebView2はWindows専用であり、MacやLinuxではElectronやQtポートが必要です。この選択は、アプリケーションがWindowsのネイティブな感触と効率的なリソース管理を求める場合に適しています。

## 不確実な点・追加確認が必要な点

記事間の食い違いや資料からは断定できない点を以下に示します。まず、記事1と記事5はそれぞれ異なるフレームワークやアプローチを検討しており、Kudzuというコンパイラファーストフレームワークのスケーラビリティについての議論と、C++ + WebView2によるWindowsデスクトップアプリケーションの開発についての議論が分離されています。記事1では、KudzuがReactの機能を再実装せずに実用的なアプリケーションにスケールする可能性を問うていますが、記事5では、ElectronではなくWebView2とC++を組み合わせたアプローチが選ばれた理由について説明しています。このため、両記事は目的や背景が異なり、直接的な比較は困難です。

また、記事3と記事4は同様にVue.jsをベースにしたマルチプラットフォームアプリケーションの実装について述べていますが、記事4はHashnodeのタグページであり、具体的な技術的詳細は記載されていません。そのため、記事3の内容をもとにした分析が主な情報源となります。さらに、記事2は、フレームワークを使わず、ネイティブモジュールとES6クラスを組み合わせて大規模なフロントエンドアプリケーションを構築する方法について議論していますが、これはコンパイラファーストフレームワークとは異なるアプローチです。

これらの記事は、それぞれ異なる技術的アプローチやフレームワークの選択肢について論じており、それらの背景や目的が明確でないため、断定的な結論を出すことはできません。また、各記事の公開日時や取得日時が不明であるため、情報の新旧や信頼性の判断が難しい点も挙げられます。
