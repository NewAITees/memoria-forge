# S3アップロードフォームがセキュリティリスクとなるケース

## 結論

S3バケットへのアップロードフォームがセキュリティ上の足がかりとなるリスクは、signed POST policyが過度に幅広い設定になっている場合に特に顕著であり、HackerOneから4つの報告書が提出されていることから、この問題の深刻さが確認されています。特に、prefixマッチを許可することで、攻撃者が意図しないキーにアクセスできる可能性が高くなるため、exactマッチの指定が必須であり、ポリシーの設計において厳密な制御が求められます。

## テーマ概要

このテーマは、アップロードフォームがセキュリティ上の足がかり（foothold）となるリスクと、S3バケットへの広範な書き込み権限を許可する仕組みの問題を扱っています。特に、signed POST policyが過度に幅広い設定になっている場合、サーバーが提供するすべてのsigned URLがS3バケット全体にわたる書き込み操作を許可してしまうという脆弱性が報告されています。HackerOneから4つの報告書が提出され、ShopifyやBCMなど異なる企業がそれぞれ異なる脆弱性パターンを指摘しています。この問題は、S3バケットのセキュリティを脅かす可能性があるため、現在注目されています。

## 共通して確認できる点

複数の記事で共通して確認できた事実として、S3バケットへの書き込み権限が過度に広範囲に設定されている場合、サーバーが提供するsigned URLは、S3バケット全体にわたる書き込み操作を許可する可能性があることが指摘されている。これは、HackerOneから提出された4つの報告書でも同様のパターンが確認されており、特にRails、Express、Djangoなどのフレームワークで生成されるsigned POST policyが、`["starts-with", "$key", "files/"]`のようなprefixマッチを許可することで、意図しないキーへの書き込みが可能になるケースが挙げられている。また、この問題は、signed POST policyがexact matchではなくprefix matchを採用していることにより、攻撃者が特定のキーにアクセスできる可能性が高くなるため、セキュリティ上の脆弱性として認識されている。

## 記事ごとの差分・視点の違い

記事「When an Upload Form Becomes a Foothold: Broad S3 Write Scope」は、S3 バケットへのアップロードフォームがセキュリティ上の足がかりとなるリスクを焦点にし、signed POST policy の設定ミスが引き起こす広範な書き込み権限の問題を詳しく説明している。この記事では、HackerOne から報告された4つのケースをもとに、ポリシーが前缀（prefix）で設定されている場合の危険性を強調し、正確なキー指定（exact）が必須であることを指摘している。また、CEL（Constraint Evaluation Language）を用いた検出方法や、Z3 を用いた達成可能性の検証手法についても触れている。  

記事「How to Build a Rotation-Safe Webhook Receiver: Verify Raw Signatures for Property Billing」は、Webhook がキー回転に耐えられるようにするための設計パターンを説明しており、署名を検証する際には常に raw body を使用すべきであると主張している。この記事では、署名検証の信頼性を高めるために、検証結果を証拠として保存し、永続的な書き込みを完了した後にのみ ACK を返す必要がある点を強調している。  

記事「Your Signature String Depends on Your Dependency Version」は、EIP-712 署名の検証に使われる hexbytes ライブラリのバージョンが、生成される署名文字列の形式に影響を与えるという問題点を指摘している。特に、バージョン 0.3.x では 0x プレフィックスが含まれるが、バージョン 1.0.0 ではそのプレフィックスが削除され、検証が失敗する可能性がある。この記事では、バージョン変更による不具合が検出が難しい点を指摘し、依存関係のバージョン管理の重要性を強調している。  

記事「Body as dependency · fastapi fastapi · Discussion #6082 · GitHub」は、FastAPI において request body を認証処理に使用する際の課題を議論しており、body を取得する方法や、body が空の場合の処理について議論している。この記事では、body が request オブジェクトに保持されないため、認証処理で body を参照できないという技術的制約を指摘し、その解決策として、body を直接取得する方法を提案している。  

記事「Как выполнить задание «Первый плацдарм» (A First Foothold)...」は、ゲーム「ARC Raiders」におけるクエスト「Первый плацдарм（A First Foothold）」の進行方法を解説している。この記事では、クエストの各ステップにおける目標地点や行動の手順を具体的に説明し、プレイヤーがどの場所に注意を払うべきかを示している。ゲーム内での位置情報や、特定のオブジェクトとの相互作用の方法についても詳しく記載されている。

## 深掘り調査で得られた知見

深掘り調査によって分かったのは、S3バケットへのアップロードフォームが攻撃者にとって足がかりとなるリスクについての詳細なパターンです。特に、signed POST policyが過度に幅広い設定になっていると、サーバーが生成するすべてのsigned URLがS3バケット全体への書き込み操作を許可してしまうという点が重要です。これは、HackerOneから4つの報告書が提出されており、それぞれが異なる脆弱性のパターンを示しています。例えば、ShopifyとBCMがそれぞれ異なる報告書を提出しており、それぞれのケースでは異なる脆弱性が発生しています。また、signed POST policyがprefixマッチを許可している場合、攻撃者はそのprefix以下のすべてのキーにアクセスできる可能性があります。一方で、exactマッチを許可している場合、アクセス可能なキーは1つに限定されます。この違いにより、攻撃の範囲が大きく異なります。したがって、signed S3アップロードポリシーでは、常にexactなオブジェクトキーにバインディングする必要があります。また、ポリシーの設定がprefixモードになっている場合、CEL（Constraint Evaluation Language）が警告を発し、その状態が不安全であると判断します。ただし、CELは「この構成は危険か？」という質問に答えるだけであり、具体的にどのキーにアクセス可能かという「到達性」の問題については、Z3などのツールを用いて検証する必要があります。このように、S3バケットへのアップロードフォームの設定が適切でない場合、攻撃者が意図しない範囲でデータを操作できる可能性があるため、セキュリティ対策として慎重なポリシー設定が求められます。

また、記事3はEIP-712署名の検証におけるバージョン依存性の問題を指摘しており、hexbytesライブラリのバージョン変更によって署名文字列のフォーマットが変化するという点を強調しています。この問題は、サーバー側の検証ロジックがバージョンに依存しているため、開発段階では検出が難しいとされています。しかし、記事1や記事5に見られるような具体的な脆弱性の例とは異なり、これはライブラリのバージョン管理やフォーマットの整合性を保つ必要性を示す技術的な課題に過ぎません。
