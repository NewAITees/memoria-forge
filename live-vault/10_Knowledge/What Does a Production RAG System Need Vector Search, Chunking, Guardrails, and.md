# Production RAGシステムの構築で必要な技術要素

## 結論

Production RAGシステムの構築において、ベクター検索とキーワード検索のハイブリッドアプローチが必須であり、チャンキング戦略の選択は検索品質とコストに大きな影響を与える。特に、正確なキーワード検索が必要なケースでは、ベクター検索単独では不十分であり、ハイブリッド検索を採用する必要がある。

## テーマ概要

Production RAG（Retrieval-Augmented Generation）システムは、大規模言語モデル（LLM）の出力をより正確で信頼性の高い情報に向上させるための技術として注目されています。この技術は、外部の文書や知識ベースから情報を検索し、LLMにその情報を基に応答を生成させることで、単純なLLMの出力に比べて質を向上させます。しかし、実際の運用では、ベクトル検索、チャンキング（文書の分割）、ガードレール（誤情報防止）、コスト制御といった要素が不可欠です。特に、ベクトル検索は概念的な類似性を捉えるのに適していますが、正確なキーワード検索（例：SKU番号、略称、人物名など）には不向きであり、ハイブリッド検索（ベクトル検索とキーワード検索の組み合わせ）が推奨されています。また、コスト制御や誤情報防止のためのガードレールは、プロダクション環境での信頼性を確保するために重要です。このような要素が複雑に絡み合い、RAGシステムの実装は技術的な挑戦を伴います。そのため、現在、RAGシステムの構築においては、これらの要素をどのように統合し、効率的に運用するかが注目されています。

## 共通して確認できる点

複数の記事では、生産用RAGシステムがベクター検索、チャンキング、ガードレール、コスト制御を含む複数の要素を必要とすることが共通して述べられている。特に、ベクター検索は概念的な類似性を捉えるには効果的だが、SKU番号や略称などの正確なキーワード検索には弱いという点が一致している。一方で、ハイブリッド検索（ベクター検索とキーワード検索の組み合わせ）は、企業の知識ベースで検索性能を10〜30%向上させることが示されている。また、チャンキング戦略は検索品質とコストに大きな影響を及ぼすとされ、誤ったチャンキングは最大で9%のrecallの差を生じる可能性がある。ガードレールは、ハルシネーションの防止や、応答が検索されたドキュメントに基づくように制御するための重要な要素とされている。コスト制御は、APIトークンの使用量を抑えるための重要な課題であり、生産環境では特に重要となる。さらに、ローカルRAGシステムは、データプライバシーを重視し、敏感なドキュメントをユーザーの機器に保つことが特徴とされている。また、生産用RAGシステムの設計では、インフラの構築よりもまず検索効果を重視し、小規模なドキュメントと実際の質問から始めることが推奨されている。

## 記事ごとの差分・視点の違い

記事ごとの立場や強調点、論点の違いは以下の通りです。

記事「What Does a Production RAG System Need? Vector Search, Chunking, Guardrails, and Cost Controls」では、RAGシステムの本格的な導入において、ベクトル検索の限界と、正確なキーワード検索の必要性が強調されています。特に、SKUや製品コードなどの正確な一致を求めるケースでは、ベクトル検索だけでは対応できず、ハイブリッド検索が必須であると述べられています。また、セキュリティ面では、RBACメタデータをインデックスクエリ内でフィルタリングする必要性が指摘されており、アクセス制御の重要性が強調されています。

記事「Production-Grade RAG Systems — Chunking, Cost Optimization, Hallucination Control & Index Selection」では、RAGシステムのコスト削減とハルカレーションの制御が中心テーマです。特に、検索結果に基づいた厳格な応答を求める必要性が強調されており、検索結果が見つからない場合の明確な返答の仕様が示されています。また、インフラの導入よりもまず小規模なドキュメントと実際の質問から始めるべきというアプローチが推奨されており、RAGシステムのプロトタイプ構築の方法論が提示されています。

記事「Local RAG starts with retrieval, not infrastructure」では、RAGシステムの構築において、インフラの導入よりもまず検索効果を重視すべきであるという立場が示されています。特に、ローカルでのテスト環境での検索効果の検証が推奨されており、データプライバシーの観点からもローカルでの実装が重視されています。また、ハイブリッド検索の必要性と、単純なキーワード検索の限界についても論じられています。

記事「GitHub - jonfairbanks/local-rag: Ingest files for retrieval ...」では、ローカルでのRAG実装に焦点を当て、イングレスされたファイルやウェブサイトの情報を利用して、ローカルでチャットや埋め込み、インデックス化されたソースコンテンツを保持する仕組みが紹介されています。また、軽量なツールを使用することで、コストを抑えたRAGシステムの構築が可能であると強調されています。

記事「I Took the Wheel Off My RAG: Managed KB vs. Manual Chunking」では、RAGシステムの導入において、チャンキング戦略の選択が性能に大きく影響するという点が強調されています。特に、Fixed Sizeチャンキングがベクトル検索のバックエンドとして最適であるという結論が示されています。また、AWSのManaged Knowledge Baseの導入により、チャンキング戦略の選択が不要となり、検索戦略の自動化が可能になったという現状が述べられており、その利点と欠点が論じられています。

## 深掘り調査で得られた知見

Production RAGシステムの構築において、ベクター検索、チャンキング、ガードレール、コスト制御は必須要素として挙げられる。特に、ベクター検索は概念的な類似性を捉えるには有効だが、SKU番号や略称、人名などの正確なキーワード検索には弱いという課題がある。そのため、ハイブリッド検索手法（例：BM25によるスパース検索とドット積によるデジスト検索の組み合わせ）が推奨され、企業の知識ベースでは検索性能を10〜30％向上させる効果があるとされている。  

チャンキング戦略は検索品質に大きな影響を及ぼし、誤った戦略は最大で9％のrecallの差を生じる可能性がある。一般的なアプローチでは、500〜1000文字程度の固定サイズチャンキングが採用されるが、内容構造に応じた動的チャンキングも提案されている。また、チャンキングのオーバーラップ率は10〜20％が効果的とされる。  

ガードレールは、hallucinationの防止や、検索結果に基づいた回答の強制を目的としており、特に生産環境では必須である。回答が知識ベースにない場合、「知識ベースにない」と明示する必要がある。  

コスト制御においては、LLMの使用を最小限に抑え、検索結果のみをLLMに提示するなどの工夫が求められる。また、ローカルRAGシステムでは、機密情報の保持やコスト削減の観点から、SQLiteやpgvectorなどの軽量技術が採用される傾向にある。  

さらに、AWSのAmazon Bedrock Managed Knowledge Baseの導入により、ユーザーがチャンキング戦略を指定する必要がなく、Smart Parsingによる自動処理やAgenticRetrieveStreamによる複雑な検索戦略が提供されるようになった。この変化により、手動チャンキングの品質とほぼ同等の結果が得られる一方で、Agentic Plannerの性能はモデルに依存し、一部の質問では正しくクエリを分解できなかった例も確認されている。

## 不確実な点・追加確認が必要な点

記事間では、RAGシステムの設計において、ベクトル検索とキーワード検索のハイブリッドアプローチが推奨されている点で一致している。しかし、具体的な実装方法や、どのケースでどちらの検索方式が優れているかについては、一貫性が見られない。たとえば、記事1では、純粋なベクトル検索が概念的類似性には適しているが、SKU番号や略称などの正確なキーワード検索には不向きであると指摘されている。一方、記事5では、製品コードや契約番号などの正確な検索にはキーワード検索が適しているが、語彙の違いが原因でキーワード検索も限界があるとされている。

また、チャンキング戦略についても、記事1では固定サイズのチャンキングが推奨されており、文章の意味を切断してしまう可能性があるとしている。一方で、記事5では、チャンキング戦略がRAGの性能に大きな影響を与えるとし、誤った戦略が最大で9%のrecallの差を生じる可能性があると指摘している。これに対して、記事2では、チャンキングのサイズやオーバーラップ率は重要な要素だが、具体的な数値や範囲については明示されていない。

さらに、記事5では、AWSのManaged Knowledge Baseが提供するAgenticRetrieveStreamの性能がモデルに依存する可能性があると指摘されており、これは記事1や記事2では言及されていない。また、記事3では、ローカルでのRAGシステム構築が推奨されており、プライバシーの観点から機密情報の保持が重視されているが、記事1や記事2では、クラウドベースのベクトルストアの使用が前提としている点が異なる。

これらの違いから、RAGシステムの設計において、どの要素が最も重要であるかは、使用ケースやデータの種類、コスト制約などによって異なり、一概に断定することはできない。そのため、各記事が提示するアプローチは、特定のシナリオに応じて選択されるべきである。
