# Trusting-Trust攻撃とLinuxディストリビューションへの影響

## 結論

Trusting-Trust攻撃は、コンパイラにバックドアを埋めることで、そのコンパイラがコンパイルするすべてのプログラムに再びバックドアを挿入する可能性のある深刻な脅威であり、2026年の論文ではLinuxディストリビューション全体に影響を及ぼす可能性が示されている。一方、CVE-2026-67276のような特定の脆弱性は、MikroTik RouterOSに特化したSSH認証バイパスの問題であり、2026年9月にパッチが公開され、実際に攻撃が行われた事実も確認されている。これらの事例は、セキュリティリスクの多様性と、対応策の迅速な実施が不可欠であることを改めて示している。

## テーマ概要

Trusting-Trust攻撃は、コンパイラにバックドアを埋めることで、そのコンパイラがコンパイルするすべてのプログラムに再びバックドアを挿入する可能性のある攻撃手法です。この攻撃は、Ken Thompsonが1984年に提示した初期のTrusting-Trust攻撃を拡張し、Linuxディストリビューション全体に影響を与える可能性を示した論文が2026年に公開されました。この論文では、コンパイラが信頼できない場合、ディストリビューションのすべてのパッケージにバックドアが含まれる可能性があるとされています。また、Trusting-Trust攻撃がLinuxディストリビューション全体に影響を及ぼす可能性があるという点で注目されており、特に再現可能なビルドやソースコードの監査などの防御策が有効であるとされています。この攻撃の危険性は、信頼性の高いコンパイラがなければ、ディストリビューションのすべてのパッケージがバックドアを含む可能性があるため、技術的にも社会的にも大きな懸念となっています。

## 共通して確認できる点

Trusting-Trust攻撃は、コンパイラにバックドアを挿入することによって、そのコンパイラがコンパイルするすべてのプログラムに再びバックドアを挿入する可能性がある攻撃手法です。この攻撃は、Linuxディストリビューション全体に影響を及ぼす可能性があることが示されています。特に、2026年7月に公開された論文では、Ken Thompsonの1984年のTrusting-Trust攻撃を拡張し、Linuxディストリビューション全体にバックドアを挿入する方法を提案しています。論文では、再現可能なビルドやソースコードの監査などの防御策が、コンパイラが信頼できる場合にのみ機能することを強調しており、コンパイラが信頼できない場合、ディストリビューションのすべてのパッケージにバックドアが含まれる可能性があるとされています。また、論文では、コンパイラのバックドアがディストリビューションのビルドパイプラインを通じて広がる可能性があることも指摘しています。

## 記事ごとの差分・視点の違い

記事「Trusting-Trust Attack against an Entire Linux Distribution」は、Ken ThompsonのTrusting-Trust攻撃を拡張し、Linuxディストリビューション全体にバックドアを挿入する手法を論じている。論文は、コンパイラが信頼できない場合、ディストリビューションのすべてのパッケージにバックドアが含まれる可能性を示しており、再現可能なビルドやソースコードの監査などの防御策が信頼できるコンパイラを前提として機能することを強調している。一方、「Trusting-Trust Attack against an Entire Linux Distribution」の記事は、論文の主張を批判し、攻撃が実際には広がる可能性を否定している。この記事では、攻撃がディストリビューションのビルドパイプラインを通じて広がるという主張を疑い、最小バイトの「シード」ブートストラップが攻撃を防ぐと主張している。  

記事「Patching Guide: Closing the CVE-2026-67276 SSH Authentication Bypass on MikroTik Routers」は、CVE-2026-67276の脆弱性の詳細と、MikroTik RouterOSへのパッチ適用の手順を説明している。この記事では、脆弱性の影響範囲や、CVE-2026-67276と関連する他の脆弱性（CVE-2026-86060、CVE-2026-67277）の修正対応についても解説しており、管理者が即座にパッチを適用する必要性を強調している。一方、「GitHub - dinosn/mikrotrick-poc:CVE-2026-67276 RouterOS SSH Authentication Bypass」は、脆弱性の技術的な仕組みや、攻撃の再現方法をコードとテスト結果を交えて詳細に説明している。この記事では、脆弱性の影響範囲や、攻撃の実行条件（ユーザー名とRSA公開鍵のモジュラス）についても具体的に記述している。  

記事「BlueMoon Campaign Exploited 27-Day Chrome Patch Gap Using AI Assisted Tools」は、Chromeのパッチギャップを悪用したBlueMoonキャンペーンの詳細を説明しており、AIが exploit の開発にどのように関与したかを示唆している。この記事では、パッチギャップの問題がソフトウェアサプライチェーンにおける構造的な問題であると指摘し、セキュリティ関連のコミットを監視する重要性を強調している。一方、他の記事は、Trusting-Trust攻撃やSSH認証バイパスの脆弱性に焦点を当てており、それぞれの技術的詳細や対応策を論じている。

## 深掘り調査で得られた知見

Trusting-Trust攻撃の新たな研究が発表され、Linuxディストリビューション全体への影響が再び注目を集めている。論文「Trusting-Trust Attack against an Entire Linux Distribution」では、コンパイラにバックドアを挿入することで、ディストリビューション内のすべてのパッケージにその影響を及ぼす可能性が示されている。この攻撃は、再現可能なビルドやソースコードの監査などの防御策が有効となる条件として、コンパイラが信頼できる場合に限られる。論文では、コンパイラが信頼できない場合、ディストリビューションのすべてのパッケージにバックドアが含まれる可能性があるとされている。また、コンパイラのバックドアがディストリビューションのビルドパイプラインを通じて広がる可能性も指摘されている。  

一方、CVE-2026-67276というSSH認証バイパスの脆弱性が発見され、MikroTik RouterOSで広範な影響を及ぼしている。この脆弱性は、RSA公開鍵の検証プロセスにおいて指数（exponent）が省略されるため、攻撃者が偽造した公開鍵で認証をバイパスできる。MikroTikは2026年9月3日にパッチを公開し、影響を受けるバージョンは7.24.2、7.23.4、6.49.21（またはそれ以降）に限定されている。この脆弱性は、未認証でリモートからルーターを制御可能にする「MikroTrick」攻撃の一部として、2026年9月2日から実際に悪用されている。  

さらに、ChromeのV8エンジンにおけるCVE-2026-85046の脆弱性が発見され、27日間のパッチギャップが悪用された「BlueMoon」キャンペーンが報告されている。このキャンペーンでは、Chrome Stableチャネルがパッチを配布するまでに27日間の間隔があり、攻撃者はその間にオープンソースの修正コミットから実用可能なエクスプロイトを逆エンジニアリングした。Proofpointは、AI支援によるエクスプロイト開発のパターンを指摘し、ソフトウェアサプライチェーンにおけるパッチギャップの問題を浮き彫りにしている。  

これらの事例は、セキュリティの重要性を再認識させるとともに、攻撃手法の進化と防御策の必要性を強調している。特に、Trusting-Trust攻撃やパッチギャップを活用したゼロデイ攻撃の増加は、今後のセキュリティ対策における新たな課題となる。

## 不確実な点・追加確認が必要な点

記事間の食い違いや、資料からは断定できない点を具体的に説明すると、Trusting-Trust攻撃に関する論文とCVE-2026-67276の脆弱性は、異なる文脈で扱われている。論文では、Trusting-Trust攻撃がLinuxディストリビューション全体に影響を及ぼす可能性があると示唆しており、コンパイラにバックドアが埋め込まれることで、すべてのパッケージにその影響が及ぶ可能性があると述べている。しかし、この論文は具体的なディストリビューション名を明示していないため、どのディストリビューションが影響を受けるかは不明である。一方、CVE-2026-67276はMikroTik RouterOSに特化したSSH認証バイパスの脆弱性であり、特定のバージョンのRouterOSが影響を受けることが明記されている。また、この脆弱性は2026年9月に修正が発表され、実際に攻撃が行われたという情報も含まれている。したがって、Trusting-Trust攻撃とCVE-2026-67276は、それぞれ異なる攻撃手法であり、対象となるシステムや時間軸も異なる。さらに、BlueMoonキャンペーンに関する情報では、Chromeのパッチギャップが攻撃に利用されたことが示されており、これはTrusting-Trust攻撃とは異なるタイプのセキュリティ脅威である。これらの情報は、それぞれ独立したセキュリティリスクとして捉えるべきであり、Trusting-Trust攻撃がLinuxディストリビューション全体に及ぼす影響についての具体的な事実が不足している。
