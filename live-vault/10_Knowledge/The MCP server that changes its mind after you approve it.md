# MCPサーバーの動的ツール説明文攻撃とその対策

## 結論

MCPサーバーのセキュリティ上の課題として、ツールの説明文が動的に取得される仕組みを悪用した攻撃が確認され、既存のセキュリティツールでは検出が困難であることが明確になった。この問題は、ツールの説明文の変更がツールの能力を変更する可能性があり、新たなセキュリティフレームワーク「Bulwark」が提案されるなど、MCPプロトコルの信頼性と安全性への関心が高まっている。

## テーマ概要

MCP（Multi-Call Protocol）サーバーは、AIアシスタントが外部データソースやツールに安全に接続できるようにするオープンソースプロトコルであり、特にAIアーキテクチャにおけるインターフェースとして注目されている。このテーマでは、MCPサーバーがユーザーが承認した後でも、動的にその動作を変更するというセキュリティ上の問題が焦点となる。具体的には、ツールの説明文が動的に取得されるため、悪意のある内容が埋め込まれる可能性があり、これにより敏感なデータの漏洩や不正なデータ転送が行われる恐れがある。このような攻撃ベクタは、従来のセキュリティツール（例：依存関係スキャナ、SASTツール、コードレビュー）では検出が困難であり、新たなセキュリティフレームワーク「Bulwark」が提案されている。Bulwarkは、ツールの説明文のハッシュをロックファイルに保存し、変更を検出する機能を持ち、不可視のテキスト（例：Unicodeタグブロック、ゼロ幅文字）を検出する能力もある。この問題は、MCPプロトコルの信頼性とセキュリティ性を問うものであり、現在のAIアシスタントの運用において重要な課題となっている。

## 共通して確認できる点

MCPサーバーの設定において、ツールの説明文が動的に取得される仕組みが存在し、これにより悪意のある内容が埋め込まれる可能性があることが複数の記事で確認されている。このような変更は、セキュリティツール（例：Dependabot、Snyk、Trivy）が検出できない攻撃ベクタとして機能する。ツールの説明文が更新されると、敏感なデータ（例：プライベートなSSHキーパス）が漏洩する可能性がある。また、Bulwarkという新しいセキュリティフレームワークが提案されており、ツールの説明文のハッシュをロックファイルに保存し、変更を検出する機能を持つ。Bulwarkは、不可視のテキスト（例：Unicodeタグブロック、ゼロ幅文字）を検出する能力も持つ。  

MCPクライアントのアイドルタイムアウトは60秒であり、テストスイートが4分かかる場合、クライアントが60秒後に呼び出しをキャンセルする。この結果、プロセスは継続して実行され、モデルはテスト結果を保持し、再実行を行うことで、2つのテストスイートが同じディレクトリで競合し、ロックエラーが発生する。octofsというオープンソースのMCPファイルシステムサーバーの開発者により、11回のリリース（0.10.1から0.14.1）でこの問題が解決された。MCPサーバーの実際のインターフェースは、モデルに返すすべての文字列であり、特に遅い文字列（モデルが待機する文字列）に焦点が当てられた。  

ephemora-cell 1.0.4はPyPIに公開され、stateless MCP tool serverとして動作し、初期化ハンドシェイクやセッションステートを必要としない。tools/listの応答にはCacheableResultフィールドが含まれており、ホストがツールリストをキャッシュできるようにしている。未知のバージョンは-32022でサポートされているリストを指定して拒否される。Handshake-eraのクライアント（Claude Desktop、VS Code、Codex）は変更なしに動作し、両方の時代を1つのプロセスでサポートしている。

## 記事ごとの差分・視点の違い

記事「The MCP server that changes its mind after you approve it」は、MCPサーバーの設定において、ツールの説明文が動的に取得される仕組みを悪用したセキュリティ脆弱性を強調しており、攻撃者がツールの説明文を改ざんして敏感なデータを漏らす可能性があることを指摘している。一方、「Fix Agent terminated due to error in Antigravity」は、MCPクライアントのアイドルタイムアウトとテストスイートの実行間に生じる競合やロックエラーをテーマにし、octofsというMCPファイルシステムサーバーの開発における改善点を解説している。記事「Waiting Is Not a Tool Call: Making an MCP server's shell event-driven」は、MCPサーバーの実際のインターフェースとして、モデルに返すすべての文字列を強調し、イベント駆動型のシェル実装を通じて待機時間の問題を解決した取り組みを紹介している。記事「muvon.io/blog/octofs-0-14-waiting-is-not-a-tool-call.md」は、octofsの11回のリリースを通じた改善点を時系列的に説明し、イベント駆動型のコマンド実行や進捗通知の導入を強調している。最後に、「ephemora-cell 1.0.4: a stateless MCP tool server, now on PyPI!!」は、statelessなMCPツールサーバーとしての特徴を強調し、キャッシュ可能なツールリストやバージョン管理の仕組みを紹介している。各記事は、MCPプロトコルのセキュリティ、実行効率、インターフェース設計、およびツールサーバーの実装形態という異なる視点から、MCPの課題と改善点を論じている。

## 深掘り調査で得られた知見

MCPサーバーのセキュリティに関する問題は、ツールの説明文が動的に取得される仕組みを悪用した攻撃が原因で発生しており、既存のセキュリティツールでは検出が困難であることが明らかになった。この攻撃ベクタは、依存関係スキャナー（例：Dependabot、Snyk、Trivy）や静的コード分析ツール（例：Semgrep、CodeQL）の対象外であり、コードレビューの差分検出も行えない状況を生み出す。このため、Bulwarkという新しいセキュリティフレームワークが提案され、ツールの説明文のハッシュをロックファイルに保存することで、変更を検出する仕組みが導入された。Bulwarkは、不可視のテキスト（例：Unicodeタグブロック、ゼロ幅文字）の検出にも対応し、攻撃者がレビューを回避する手段を封じる。また、ツールの説明文の変更がツールの能力を変更する可能性があるため、検出ルールよりも優れた検出方法として位置付けられている。

一方で、MCPクライアントのアイドルタイムアウトが60秒であり、テストスイートが4分かかる場合、クライアントが呼び出しをキャンセルしてしまう問題も発生していた。これは、テストが完了するまでに時間がかかり、プロセスが継続して実行されるため、モデルがテスト結果を保持し、再実行を行うことで、競合やロックエラーが発生する原因となった。この問題は、octofsというオープンソースのMCPファイルシステムサーバーの開発者により、11回のリリース（0.10.1から0.14.1）で解決された。これらのリリースでは、MCPサーバーの実際のインターフェースがモデルに返すすべての文字列であり、特にモデルが待機する遅い文字列に焦点を当てた。シェルはイベント駆動になり、コマンドが10秒以上実行されると自動的に背景に移動し、完了時にクライアントに通知されるようになった。0.10.2では、コマンドが実行中であれば10秒ごとに進捗通知を送る「レーダー」が追加され、60秒のアイドルタイムアウトによる呼び出しキャンセルの問題が解消された。

また、ephemora-cell 1.0.4はPyPIに公開され、stateless MCP tool serverとして動作し、初期化ハンドシェイクやセッションステートを必要としない。tools/listの応答にはCacheableResultフィールドが含まれており、ホストがツールリストをキャッシュできるようにしている。未知のバージョンは-32022でサポートされているリストを指定して拒否される。Handshake-eraのクライアント（Claude Desktop、VS Code、Codex）は変更なしに動作し、両方の時代を1つのプロセスでサポート。バージョンは単一ソースで管理され、pyproject.toml とランタイムバージョンが一致することをテストで強制。llama.cpp MCPは、7Bモデルでも動作し、OpenAI-互換APIのTool Callsとは別に動作。Playwright MCPサーバーは、ブラウザ自動化を提供し、LLMsがウェブページと構造化されたアクセシビリティスナップショットを通じてインタラクティブに動作可能となった。

## 不確実な点・追加確認が必要な点

記事間の食い違いや、資料からは断定できない点を具体的に挙げると、以下の通りです。まず、記事1と記事3では、MCPサーバーのセキュリティに関する問題点が異なる表現で説明されています。記事1では、ツールの説明文が動的に取得され、悪意のある内容が埋め込まれる可能性があると述べられており、これはセキュリティツールが検出できない攻撃ベクタとして位置付けられています。一方で、記事3では、MCPクライアントのアイドルタイムアウトが60秒であり、テストスイートが4分かかるため、クライアントが呼び出しをキャンセルするという状況が記述されています。この点では、セキュリティに関する直接的な問題ではなく、MCPプロトコルの挙動に関する技術的な課題が強調されています。

また、記事4と記事5は、MCPサーバーの実装に関する技術的な改善点を述べています。記事4では、MCPサーバーの実際のインターフェースがモデルに返すすべての文字列であり、特にモデルが待機する遅い文字列に焦点を当てた改善が行われたとされています。一方で、記事5では、ephemora-cell 1.0.4がPyPIに公開され、stateless MCP tool serverとして動作すること、ツールリストのキャッシュ機能やバージョン管理の仕組みが導入されたとされています。これらは、MCPサーバーの実装における技術的進化を示すものですが、具体的な利用シーンや実際の導入事例については記載されていません。

さらに、記事2では、Google Antigravityにおいて「Error Agent execution terminated due to an error」というエラーメッセージが発生する原因として、MCPサーバーが関与している可能性があるとされています。ただし、この記事はYouTubeの動画であり、詳細な技術的な説明は行われていません。そのため、MCPサーバーがこのエラーにどのように関与しているのか、具体的な原因や対処方法については明確ではありません。

これらの記事は、MCPサーバーに関する技術的課題やセキュリティ上の懸念、実装改善の方向性についての情報を提供していますが、それぞれの記事が扱う焦点や深掘りのレベルが異なり、一貫した視点での情報が得られていません。そのため、MCPサーバーの全体像を把握するには、これらの情報が相互に補完する必要があり、単独では断定的な結論を導き出すことはできません。
